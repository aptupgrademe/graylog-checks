check_graylog_zabbix.py – Documentación

Script de comprobación nativo de Zabbix para Graylog · proyecto hermano de graylog-checks/icinga · Estado: julio de 2026

Guía de lectura Objetivo y decisión explica por qué existe esta variante como script independiente (no solo una copia de la versión de Icinga); GRAYLOG-CONCEPTS.html (un nivel más arriba) explica en detalle qué significan los distintos valores de Graylog, por si Graylog es nuevo; Instalación estándar es la guía paso a paso propiamente dicha para vuestro entorno real; Verificación en vivo muestra que esto realmente se probó, no que se ensambló solo siguiendo la documentación.

Objetivo y decisión: ¿por qué un script propio en lugar de reutilizar?

Para Zabbix había dos caminos posibles, y Raphael decidió deliberadamente por el más laborioso pero más limpio:

EnfoqueFuncionamientoEvaluación
1. Wrapper de UserParameter Invocar sin modificar el script existente de Icinga2 (check_graylog.py) mediante un UserParameter de Zabbix. Toda la salida de texto ("GRAYLOG WARNING - ...") termina como valor de tipo string en un item de Zabbix. descartado Rápido de implementar, pero poco idiomático para Zabbix: los umbrales quedan en el script en lugar de en los triggers de Zabbix, y el texto de perfdata habría que volver a analizarlo laboriosamente en Zabbix para obtener valores numéricos para las gráficas.
2. Modo nativo de Zabbix (este script) Script independiente; cada llamada entrega exactamente un valor bruto (número o cadena corta) sin ninguna evaluación. Los umbrales (WARNING/CRITICAL) se definen como expresiones de trigger de Zabbix, no en el script. implementado Se ajusta al propio modelo de item/trigger de Zabbix, los valores son directamente utilizables para gráficas, los umbrales pueden ajustarse en el propio Zabbix sin modificar el script.

La lógica subyacente de la API de Graylog (autenticación, endpoints, nombres de campos JSON) es idéntica en ambos scripts y ya fue verificada para la variante de Icinga2 contra una instancia real de Graylog — solo difiere la forma de salida.

¿Qué se mide realmente?

Una explicación detallada, escrita para quienes empiezan con Graylog, de todos los valores medidos (journal, salud del clúster, inputs, throughput, nodos, métricas internas) — incluidas analogías y por qué cada valor individual es operativamente importante — se encuentra de forma centralizada (válida para ambas variantes) en:

→ GRAYLOG-CONCEPTS.html

Resumen para quien tenga prisa El journal (graylog.journal.*) es el valor más importante — es el almacén intermedio donde esperan los mensajes cuando el indexador no da abasto. Si se llena, se pierden mensajes. Todo lo demás (salud del clúster, inputs, throughput, nodos) cubre otros tipos de fallo independientes que el journal por sí solo no muestra.

Funcionamiento: modelo de items de Zabbix (a diferencia de Icinga2)

Los plugins de Icinga2/Nagios se evalúan a sí mismos (código de salida 0-3 + salida de texto). Zabbix lo separa estrictamente en dos pasos:

PasoQuién lo haceAquí
1. Obtener el valorUn UserParameter en el agente de Zabbix invoca un comando cuya salida estándar completa se toma como valor del itemcheck_graylog_zabbix.py --mode journal-utilization devuelve, por ejemplo, solo 0.0
2. Evaluar el valorUn trigger en el servidor Zabbix, definido como expresión sobre el último valor conocido (o histórico) del itemlast(/Host/graylog.journal.utilization)>80

La diferencia decisiva: los umbrales (80 %, 95 %, ...) en Zabbix no están en el script, sino que se mantienen como trigger directamente en Zabbix — modificables en cualquier momento, sin tocar el UserParameter ni el script.

Todos los modos en detalle

15 modos mediante --mode, cada uno entrega exactamente un valor por stdout, código de salida 0 en caso de éxito, 1 ante cualquier error (inalcanzable, autenticación fallida, campo faltante):

ModoValor devueltoSignificado
lbstatusString: ALIVE/THROTTLED/DEADEstado de salud propio de Graylog
cluster-statusString: green/yellow/redSalud del clúster indexador
cluster-shards-unassignedEnteroNúmero de shards sin asignar
journal-utilizationNúmero de coma flotante, 0-100Ocupación del journal en %
journal-uncommittedEnteroMensajes en espera en el journal
journal-read-rate / journal-write-rateNúmeroMensajes/seg. leídos o escritos
inputs-total / inputs-running / inputs-failedEnteroNúmero de inputs configurados/en ejecución/fallidos
throughputEnteroMensajes/seg. a nivel de todo el clúster
nodes-total / nodes-unhealthyEnteroNúmero de nodos de Graylog totales/no saludables
metriccualquiera (passthrough)Acceso genérico a cualquier métrica interna de Dropwizard, necesita --metric-name + --field
list-metrics-lldJSON de LLD de ZabbixNo es un valor medido, sino un formato de descubrimiento para Low Level Discovery (véase abajo)

Particularidad: list-metrics-lld — Low Level Discovery de Zabbix

En lugar de entregar solo una lista de texto para búsqueda manual, como en Icinga2, este modo devuelve el formato nativo de JSON de LLD de Zabbix: 

{"data": [{"{#METRICNAME}": "org.graylog2.journal.append.1-sec-rate"}, ...]}

Esto puede incorporarse directamente como regla de descubrimiento en Zabbix para generar automáticamente prototipos de item para todas las métricas encontradas — una función de Zabbix para la que no existe un equivalente directo en Icinga2.

lbstatus: la misma corrección de error que en Icinga2

/system/lbstatus responde con Content-Type: text/plain y con el estado en el propio código de estado HTTP (200/429/503), no en el cuerpo. El script consulta este endpoint específicamente con Accept: */* (no application/json como en los demás modos) — de lo contrario Graylog devuelve 406 Not Acceptable. Este error se encontró durante la prueba en vivo de la variante de Icinga2 y aquí está implementado correctamente desde el principio.

Autenticación

Idéntico a la variante de Icinga2: token de API de Graylog como HTTP Basic Auth, el token como nombre de usuario, la cadena literal "token" como contraseña.

El rol Reader NO es suficiente para metric/list-metrics-lld Confirmado en vivo (véase Verificación en vivo): con el rol Reader puro los endpoints /system/metrics/* devuelven 403 Not authorized. Los otros 12 modos funcionan sin problemas con Reader. Para los dos modos de métricas, añadir además cuatro permisos al usuario: 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'

Configuración de UserParameter

El archivo userparameter_graylog.conf de esta carpeta se coloca en el agente de Zabbix (no en el servidor): 

UserParameter=graylog.lbstatus,python3 /pfad/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode lbstatus
UserParameter=graylog.journal.utilization,python3 /pfad/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode journal-utilization
...
UserParameter=graylog.metric[*],python3 /pfad/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode metric --metric-name $1 --field $2
Items parametrizados con [*] La última línea muestra el mecanismo de Zabbix para items parametrizados: graylog.metric[jvm.memory.heap.usage,value] como clave de item en Zabbix pasa jvm.memory.heap.usage como $1 y value como $2 al comando UserParameter. Probado en vivo, funciona como se esperaba (véase abajo).

Tras cualquier cambio en este archivo hay que recargar el agente de Zabbix (systemctl restart zabbix-agent2 o zabbix-agentd según la versión).

Instalación estándar (entorno real de Zabbix)

Partiendo de una instalación estándar de servidor y agente Zabbix ya en funcionamiento (instalación por paquetes, no el montaje de prueba con Docker).

  1. Crear un usuario Reader en Graylog + generar un token de API — procedimiento idéntico al de la variante de Icinga2, véase ../icinga/INSTALL.md, pasos 1-3 (solo el paso 2, los permisos de métricas, es necesario también aquí, si van a usarse metric/list-metrics-lld).
  2. Copiar el script al host del agente de Zabbix (no al servidor — el agente es quien ejecuta los comandos UserParameter, no el servidor): 
    cp scripts/check_graylog_zabbix.py /usr/lib/zabbix/externalscripts/
chmod +x /usr/lib/zabbix/externalscripts/check_graylog_zabbix.py
    Python 3 + python3-requests deben estar instalados en este host.
  3. Instalar el archivo UserParameter, ajustando URL/token en cada línea: 
    cp userparameter_graylog.conf /etc/zabbix/zabbix_agent2.d/
systemctl restart zabbix-agent2
  4. Probar antes de configurar Zabbix que el agente entrega correctamente los valores por sí mismo: 
    zabbix_agent2 -t graylog.journal.utilization
# Salida esperada: graylog.journal.utilization  [s|<número>]
# "s" = success. Con "e" (error) hay un problema con la ruta/token/red.
  5. Crear el host en Zabbix (interfaz web: Data collection → Hosts → Create host), apuntando la interfaz de agente a la IP del host del agente.
  6. Crear items para cada valor deseado — tipo "Zabbix agent", clave exactamente como en el archivo UserParameter (p. ej. graylog.journal.utilization), eligiendo el tipo de valor adecuado (numeric float para valores porcentuales, numeric unsigned para contadores, character para strings de estado como cluster-status).
  7. Crear triggers para los umbrales, por ejemplo: 
    last(/<host>/graylog.journal.utilization)>80   -> Warning
last(/<host>/graylog.journal.utilization)>95   -> High
last(/<host>/graylog.cluster.status)<>"green"  -> Warning
  8. Tras un intervalo de sondeo (delay del item, p. ej. 30s), revisar los valores del item y el estado del trigger en el frontend de Zabbix, en Monitoring → Latest data o Monitoring → Problems.
Ajustar antes del funcionamiento en producción
  • Los umbrales de trigger propuestos aquí (80 %/95 %) surgieron contra una instancia de prueba vacía, no están validados contra vuestro volumen real de mensajes.
  • nodes-unhealthy por sí solo no detecta de forma fiable un fallo completo de un nodo (un nodo ausente simplemente deja de aparecer en la lista de nodos) — comprobar además nodes-total contra el número conocido de nodos mediante un trigger (last(...)<<número esperado>).
  • TLS/certificados autofirmados: añadir --insecure como argumento adicional en la línea de UserParameter si es necesario.

Verificación en vivo (2026-07-24)

Al igual que con la variante de Icinga2, no se construyó solo siguiendo la documentación, sino que se probó contra un entorno real de Zabbix montado con Docker Compose (Zabbix Server + Zabbix Web + PostgreSQL + Zabbix Agent2, imágenes oficiales de Zabbix, la etiqueta :latest resuelta en el momento de la prueba a Zabbix 7.4.12) en la misma VM de pruebas que Graylog.

Corrección: aquí también se probó primero por error contra Graylog 6.1 El mismo desajuste de versiones que en la variante de Icinga2 (véase la Verificación en vivo correspondiente): la primera prueba de este script (prueba de agente, creación de item/trigger) se ejecutó contra graylog/graylog:6.1, no contra la versión que correspondía a la especificación OpenAPI. Tras la consulta de Raphael, el stack de pruebas de Graylog se cambió a graylog/graylog:7.1.3 (+ mongo:7.0, requisito obligatorio de 7.1.3) y se repitió la prueba completa de Zabbix — prueba de agente, nuevo token de API, valores de item, evaluación de trigger. Resultado: idéntico, ninguno de los 15 modos se comportó de forma distinta en 6.1 que en 7.1.3.

Pasos de prueba y resultados

  1. Los 15 modos ejecutados individualmente contra la API real de Graylog (no a través de Zabbix, directamente con python3 check_graylog_zabbix.py) — todos entregaron valores brutos correctos y plausibles, p. ej. journal-utilization: 0.0, cluster-status: yellow, nodes-total: 1.
  2. Contenedor de agente de Zabbix montado, archivo UserParameter incluido, Python3 + requests instalados posteriormente en el contenedor (la imagen oficial del agente de Zabbix no los incluye — igual que antes con el contenedor de Icinga2).
  3. Prueba del lado del agente (zabbix_agent2 -t <clave>) confirma éxito para todas las claves probadas: 
    graylog.journal.utilization                   [s|0.0]
graylog.lbstatus                              [s|ALIVE]
graylog.cluster.status                        [s|yellow]
graylog.throughput                            [s|0]
graylog.nodes.total                           [s|1]
graylog.metric[jvm.memory.heap.usage,value]   [s|0.1861647253430262]
    La última entrada confirma también que la sintaxis parametrizada [*] funciona tal como se documenta.
  4. Ciclo completo del servidor confirmado a través de la API de Zabbix: un host, dos items (graylog.journal.utilization, graylog.cluster.status) y un trigger (last(...cluster.status)<>"green") creados en vivo a través de la API JSON-RPC de Zabbix. Consultados tras un ciclo de sondeo desde el propio servidor (no la prueba de agente, sino los valores realmente almacenados por el servidor): 
    Item "Graylog Journal Utilization": lastvalue = "0"
Item "Graylog Cluster Status":      lastvalue = "yellow"
Trigger "Graylog indexer cluster not green on {HOST.NAME}": value = "1"  (PROBLEM)

    (Esta ejecución todavía contra Graylog 6.1, antes de la corrección de versión.)

  5. Reprueba contra Graylog 7.1.3: se creó un nuevo usuario Reader + token en la instancia 7.1.3 recién montada, y se actualizó el archivo UserParameter y los dos items/el trigger creados con el nuevo token. La prueba de agente volvió a ser exitosa (graylog.cluster.status [s|green] inmediatamente después del cambio, más adelante en la prueba también de nuevo yellow – fluctuación normal en un OpenSearch de nodo único recién creado, no es un error). El trigger se mantuvo correctamente en "PROBLEM" a lo largo de ambos estados, en cuanto el valor no era exactamente "green" – confirma que la reactividad en vivo de todo el ciclo funciona sin cambios también en 7.1.3.
Esto significa en concreto El trigger realmente se disparó (estado "PROBLEM"), porque cluster-status = "yellow" y no "green" — exactamente el comportamiento esperado. Con esto queda confirmado el ciclo completo: el servidor Zabbix consulta al agente → el agente ejecuta el comando UserParameter → el script consulta la API real de Graylog → el valor bruto vuelve al servidor → se almacena como item → la expresión del trigger se evalúa correctamente. No solo "debería funcionar según la documentación", sino realmente comprobado de principio a fin.

Diferencia respecto a la verificación de Icinga2: no se repitió la prueba de permisos de la API

La laguna de permisos de métricas (el rol Reader no basta para /system/metrics/*) ya se encontró y corrigió con la variante de Icinga2 contra la misma instancia de Graylog (el usuario de prueba con los permisos añadidos es el mismo) — aquí solo se volvió a comprobar el propio modo metric, sin investigar de nuevo desde cero la cuestión de permisos.

Puntos pendientes

  • Solo 2 de las 15 claves de item se vincularon a un trigger real en Zabbix (journal.utilization, cluster.status) — el resto solo se probó a nivel de agente (zabbix_agent2 -t), sin conectarlas con triggers propios en Zabbix
  • list-metrics-lld solo se probó como salida bruta, sin incorporarse realmente como regla de descubrimiento en Zabbix (no se verificaron prototipos de item generados automáticamente)
  • Probado contra una instancia de Graylog vacía y nueva, sin carga real de mensajes — los umbrales de trigger para producción no están validados
  • El escenario multi-nodo (nodes-total > 1) no se probó, ya que el entorno de prueba solo tenía un nodo de Graylog
