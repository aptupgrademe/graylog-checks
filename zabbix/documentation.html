check_graylog_zabbix.py – Documentation

Native Zabbix check script for Graylog · sibling project to graylog-checks/icinga · as of: July 2026

Reading roadmap Goal & Decision explains why this variant exists as a standalone script at all (not just a copy of the Icinga version); GRAYLOG-CONCEPTS.html (one level up) explains in detail what the individual Graylog values mean, in case Graylog is new to you; Standard Installation is the actual step-by-step guide for your real environment; Live Verification shows that this was really tested, not just assembled from documentation.

Goal & Decision: Why a Separate Script Instead of Reuse?

There were two possible paths for Zabbix, and Raphael deliberately chose the more involved, cleaner one:

ApproachHow it worksAssessment
1. UserParameter wrapper Call the existing Icinga2 script (check_graylog.py) unchanged via a Zabbix UserParameter. The entire text output ("GRAYLOG WARNING - ...") ends up as a string value in a Zabbix item. rejected Quick to implement, but not idiomatic for Zabbix: thresholds live in the script instead of in Zabbix triggers, and the perfdata text would have to be laboriously re-parsed in Zabbix just to get numeric values for graphs.
2. Native Zabbix mode (this script) A standalone script where every call returns exactly one raw value (a number or short string) with no evaluation at all. Thresholds (WARNING/CRITICAL) are defined as Zabbix trigger expressions, not in the script. implemented Matches Zabbix's own item/trigger model, values are directly usable for graphs, and thresholds can be adjusted in Zabbix itself without touching the script.

The underlying Graylog API logic (authentication, endpoints, JSON field names) is identical in both scripts and was already verified against a real Graylog instance for the Icinga2 variant — only the output form differs.

What Is Actually Being Measured?

A detailed explanation, written for Graylog newcomers, of all measured values (journal, cluster health, inputs, throughput, nodes, internal metrics) — including analogies and why each individual value matters operationally — lives centrally (applies to both variants) at:

→ GRAYLOG-CONCEPTS.html

Short version for the impatient The journal (graylog.journal.*) is the most important value — it's the buffer where messages wait when the indexer can't keep up. If it fills up, messages get lost. Everything else (cluster health, inputs, throughput, nodes) covers other, independent failure modes that the journal alone doesn't show.

How It Works: Zabbix Item Model (in Contrast to Icinga2)

Icinga2/Nagios plugins evaluate themselves (exit code 0-3 + text output). Zabbix strictly splits this into two steps:

StepWho does itHere
1. Fetch the valueA UserParameter in the Zabbix agent calls a command whose entire standard output is taken as the item valuecheck_graylog_zabbix.py --mode journal-utilization outputs just 0.0, for instance
2. Evaluate the valueA trigger in the Zabbix server, defined as an expression over the most recent (or historical) item valuelast(/Host/graylog.journal.utilization)>80

The key difference: in Zabbix the thresholds (80 %, 95 %, ...) are not in the script, but are maintained as triggers directly in Zabbix — changeable at any time, without touching the UserParameter or the script.

All Modes in Detail

15 modes via --mode, each outputting exactly one value to stdout, exit code 0 on success, 1 on any error (unreachable, auth failed, field missing):

ModeReturn valueMeaning
lbstatusString: ALIVE/THROTTLED/DEADGraylog's own health status
cluster-statusString: green/yellow/redIndexer cluster health
cluster-shards-unassignedIntegerNumber of unassigned shards
journal-utilizationFloat, 0-100Journal utilization in %
journal-uncommittedIntegerMessages waiting in the journal
journal-read-rate / journal-write-rateNumberMessages/sec read or written
inputs-total / inputs-running / inputs-failedIntegerNumber of configured/running/failed inputs
throughputIntegerCluster-wide messages/sec
nodes-total / nodes-unhealthyIntegerNumber of Graylog nodes total/unhealthy
metricarbitrary (passthrough)Generic access to any internal Dropwizard metric, needs --metric-name + --field
list-metrics-lldZabbix LLD JSONNot a measurement, but a discovery format for Low-Level Discovery (see below)

Special case: list-metrics-lld — Zabbix Low-Level Discovery

Instead of just outputting a text list for manual searching as with Icinga2, this mode delivers the native Zabbix LLD JSON format: 

{"data": [{"{#METRICNAME}": "org.graylog2.journal.append.1-sec-rate"}, ...]}

This can be plugged directly into Zabbix as a discovery rule, to automatically generate item prototypes for all metrics found — a Zabbix feature with no direct equivalent in Icinga2.

lbstatus: the same bug fix as in Icinga2

/system/lbstatus responds with Content-Type: text/plain and the status in the HTTP status code itself (200/429/503), not in the body. The script specifically requests with Accept: */* here (not application/json as in the other modes) — otherwise Graylog returns 406 Not Acceptable. This bug was found during the live test of the Icinga2 variant and is implemented correctly here from the start.

Authentication

Identical to the Icinga2 variant: Graylog API token as HTTP Basic Auth, token as username, the literal string "token" as password.

The Reader role is NOT enough for metric/list-metrics-lld Confirmed live (see Live Verification): with a pure Reader role, the /system/metrics/* endpoints return 403 Not authorized. All other 12 modes work fine with Reader. For the two metric modes, set four additional permissions on the user: 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'

UserParameter Configuration

File userparameter_graylog.conf in this folder, deployed on the Zabbix agent (not the server): 

UserParameter=graylog.lbstatus,python3 /path/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode lbstatus
UserParameter=graylog.journal.utilization,python3 /path/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode journal-utilization
...
UserParameter=graylog.metric[*],python3 /path/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode metric --metric-name $1 --field $2
Parameterized items with [*] The last line shows Zabbix's mechanism for parameterized items: graylog.metric[jvm.memory.heap.usage,value] as the item key in Zabbix passes jvm.memory.heap.usage as $1 and value as $2 to the UserParameter command. Tested live, works as expected (see below).

After any change to this file, the Zabbix agent must be reloaded (systemctl restart zabbix-agent2 or zabbix-agentd depending on the version).

Standard Installation (Real Zabbix Environment)

Starting from an already-running standard Zabbix server and agent installation (package installation, not a Docker test setup).

  1. Create a Reader user in Graylog + generate an API token — identical procedure to the Icinga2 variant, see ../icinga/INSTALL.md, steps 1-3 (only step 2, the metrics permissions, is also needed here if metric/list-metrics-lld are to be used).
  2. Copy the script onto the Zabbix agent host (not the server — the agent runs UserParameter commands, not the server): 
    cp scripts/check_graylog_zabbix.py /usr/lib/zabbix/externalscripts/
chmod +x /usr/lib/zabbix/externalscripts/check_graylog_zabbix.py
    Python 3 + python3-requests must be installed on this host.
  3. Install the UserParameter file, adjusting the URL/token in every line: 
    cp userparameter_graylog.conf /etc/zabbix/zabbix_agent2.d/
systemctl restart zabbix-agent2
  4. Test before configuring Zabbix that the agent itself returns the values correctly: 
    zabbix_agent2 -t graylog.journal.utilization
# Expected output: graylog.journal.utilization  [s|<number>]
# "s" = success. On "e" (error), the path/token/network is wrong.
  5. Create the host in Zabbix (web UI: Data collection → Hosts → Create host), pointing the agent interface at the IP of the agent host.
  6. Create items for each desired value — type "Zabbix agent", key exactly as in the UserParameter file (e.g. graylog.journal.utilization), choosing the appropriate value type (numeric float for percentage values, numeric unsigned for counters, character for status strings like cluster-status).
  7. Create triggers for the thresholds, e.g.: 
    last(/<host>/graylog.journal.utilization)>80   -> Warning
last(/<host>/graylog.journal.utilization)>95   -> High
last(/<host>/graylog.cluster.status)<>"green"  -> Warning
  8. After one poll interval (item delay, e.g. 30s), check the item values and trigger status in the Zabbix frontend under Monitoring → Latest data or Monitoring → Problems.
Adjust before going to production
  • The trigger thresholds suggested here (80 %/95 %) were derived against an empty test instance, not validated against your real message volume.
  • nodes-unhealthy alone does not reliably detect a complete node outage (a missing node simply no longer appears in the node list) — additionally check nodes-total against the known node count via a trigger (last(...)<<expected count>).
  • TLS/self-signed certificates: add --insecure as an additional argument on the UserParameter line if needed.

Live Verification (2026-07-24)

As with the Icinga2 variant, this was not just built from documentation but tested against a real Zabbix environment set up via Docker Compose (Zabbix Server + Zabbix Web + PostgreSQL + Zabbix Agent2, official Zabbix images, tag :latest resolved at test time to Zabbix 7.4.12) on the same test VM as Graylog.

Correction: here too, initially tested accidentally against Graylog 6.1 The same version mismatch as with the Icinga2 variant (see its Live Verification): the first test run of this script (agent test, item/trigger creation) ran against graylog/graylog:6.1, not the version matching the OpenAPI specification. After Raphael raised the question, the Graylog test stack was switched to graylog/graylog:7.1.3 (+ mongo:7.0, a hard requirement of 7.1.3) and the entire Zabbix test was repeated — agent test, new API token, item values, trigger evaluation. Result: identical, none of the 15 modes behaved differently at 6.1 than at 7.1.3.

Test steps and results

  1. All 15 modes run individually against the real Graylog API (not through Zabbix, directly via python3 check_graylog_zabbix.py) — all returned correct, plausible raw values, e.g. journal-utilization: 0.0, cluster-status: yellow, nodes-total: 1.
  2. Zabbix agent container set up, UserParameter file mounted in, Python3 + requests installed in the container afterwards (the official Zabbix agent image doesn't include it — just like with the Icinga2 container earlier).
  3. Agent-side test (zabbix_agent2 -t <key>) confirmed success for all keys tested: 
    graylog.journal.utilization                   [s|0.0]
graylog.lbstatus                              [s|ALIVE]
graylog.cluster.status                        [s|yellow]
graylog.throughput                            [s|0]
graylog.nodes.total                           [s|1]
graylog.metric[jvm.memory.heap.usage,value]   [s|0.1861647253430262]
    The last entry also confirms the parameterized [*] syntax works as documented.
  4. Full server cycle confirmed via the Zabbix API: a host, two items (graylog.journal.utilization, graylog.cluster.status), and one trigger (last(...cluster.status)<>"green") created live via the Zabbix JSON-RPC API. Queried after one poll cycle from the server itself (not the agent test, but the values actually stored by the server): 
    Item "Graylog Journal Utilization": lastvalue = "0"
Item "Graylog Cluster Status":      lastvalue = "yellow"
Trigger "Graylog indexer cluster not green on {HOST.NAME}": value = "1"  (PROBLEM)

    (This run still against Graylog 6.1, before the version correction.)

  5. Re-test against Graylog 7.1.3: a new Reader user + token created on the freshly set up 7.1.3 instance, the UserParameter file and the two created items/the trigger switched over to the new token. Agent test successful again (graylog.cluster.status [s|green] immediately after the switch, later in the test run also back to yellow – normal fluctuation for a fresh single-node OpenSearch, not an error). The trigger stayed correctly in "PROBLEM" across both states, whenever the value wasn't exactly "green" – confirming that the live responsiveness of the whole loop still works unchanged at 7.1.3 as well.
What this means concretely The trigger is actually fired (state "PROBLEM"), because cluster-status = "yellow" and not "green" — exactly the expected behavior. This confirms the entire loop: Zabbix server polls the agent → the agent runs the UserParameter command → the script queries the real Graylog API → the raw value flows back to the server → stored as an item → the trigger expression evaluated correctly. Not just "should work according to the docs," but actually run through end to end.

Difference from the Icinga2 verification: no repeat of the API permission test

The metrics permission gap (Reader role isn't enough for /system/metrics/*) had already been found and fixed against the same Graylog instance during the Icinga2 variant (the test user with the added permissions is the same one) — here only the metric mode itself was checked again, without re-investigating the permission question from scratch.

Open Items

  • Only 2 of 15 item keys were wired up to a real trigger in Zabbix (journal.utilization, cluster.status) — the rest were only tested at the agent level (zabbix_agent2 -t), not wired to their own triggers in Zabbix
  • list-metrics-lld was only tested as raw output, not actually plugged in as a discovery rule in Zabbix (no automatically generated item prototypes verified)
  • Tested against an empty, fresh Graylog instance with no real message load — trigger thresholds for production use have not been validated
  • Multi-node scenario (nodes-total > 1) not tested, since the test environment had only a single Graylog node
