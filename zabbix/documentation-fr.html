check_graylog_zabbix.py – Documentation

Script de vérification Zabbix natif pour Graylog · Projet frère de graylog-checks/icinga · État : juillet 2026

Plan de lecture Objectif et décision explique pourquoi cette variante existe comme script autonome (et pas seulement une copie de la version Icinga) ; GRAYLOG-CONCEPTS.html (un niveau au-dessus) explique en détail la signification des différentes valeurs Graylog, si Graylog est nouveau pour vous ; Installation standard est le guide pas à pas proprement dit pour votre environnement réel ; Vérification en conditions réelles montre que cela a vraiment été testé, et pas seulement assemblé d'après la documentation.

Objectif et décision : pourquoi un script propre plutôt qu'une réutilisation ?

Il y avait deux voies possibles pour Zabbix, et Raphael a délibérément choisi la plus exigeante, la plus propre :

ApprocheFonctionnementÉvaluation
1. Wrapper UserParameter Appeler le script Icinga2 existant (check_graylog.py) tel quel via un UserParameter Zabbix. La sortie texte complète ("GRAYLOG WARNING - ...") se retrouve comme valeur chaîne dans un item Zabbix. écarté Rapide à mettre en œuvre, mais peu idiomatique pour Zabbix : les seuils sont dans le script plutôt que dans les triggers Zabbix, et le texte des perfdata devrait être péniblement réanalysé dans Zabbix pour en extraire des valeurs numériques pour les graphiques.
2. Mode Zabbix natif (ce script) Script autonome, chaque appel renvoie exactement une valeur brute (nombre ou courte chaîne) sans aucune évaluation. Les seuils (WARNING/CRITICAL) sont définis comme des expressions de trigger Zabbix, pas dans le script. implémenté Correspond au modèle propre à Zabbix d'item/trigger, les valeurs sont directement utilisables pour les graphiques, les seuils peuvent être ajustés dans Zabbix lui-même sans modifier le script.

La logique sous-jacente d'accès à l'API Graylog (authentification, points de terminaison, noms de champs JSON) est identique dans les deux scripts et a déjà été vérifiée contre une véritable instance Graylog pour la variante Icinga2 — seule la forme de la sortie diffère.

Que mesure-t-on exactement ?

Une explication détaillée, écrite pour les débutants en Graylog, de toutes les valeurs mesurées (journal, santé du cluster, inputs, débit, nœuds, métriques internes) — avec des analogies et l'importance opérationnelle de chaque valeur — se trouve de façon centralisée (valable pour les deux variantes) à :

→ GRAYLOG-CONCEPTS.html

Résumé pour les pressés Le journal (graylog.journal.*) est la valeur la plus importante — c'est la mémoire tampon où les messages attendent lorsque l'indexeur ne suit pas le rythme. S'il se remplit, des messages sont perdus. Tout le reste (santé du cluster, inputs, débit, nœuds) couvre d'autres types de pannes indépendantes, que le journal seul ne montre pas.

Fonctionnement : modèle d'item Zabbix (par rapport à Icinga2)

Les plugins Icinga2/Nagios s'évaluent eux-mêmes (code de sortie 0-3 + sortie texte). Zabbix sépare cela strictement en deux étapes :

ÉtapeQui le faitIci
1. Récupérer la valeurUn UserParameter dans l'agent Zabbix appelle une commande dont toute la sortie standard est reprise comme valeur d'itemcheck_graylog_zabbix.py --mode journal-utilization ne renvoie par ex. que 0.0
2. Évaluer la valeurUn trigger dans le serveur Zabbix, défini comme une expression portant sur la dernière valeur connue (ou historique) de l'itemlast(/Host/graylog.journal.utilization)>80

La différence décisive : chez Zabbix, les seuils (80 %, 95 %, ...) ne se trouvent pas dans le script, mais sont gérés directement dans Zabbix sous forme de triggers — modifiables à tout moment, sans toucher au UserParameter ni au script.

Tous les modes en détail

15 modes via --mode, chacun affiche exactement une valeur sur stdout, code de sortie 0 en cas de succès, 1 pour toute erreur (injoignable, authentification échouée, champ manquant) :

ModeValeur de retourSignification
lbstatusChaîne : ALIVE/THROTTLED/DEADÉtat de santé propre à Graylog
cluster-statusChaîne : green/yellow/redSanté du cluster d'indexation
cluster-shards-unassignedEntierNombre de shards non assignés
journal-utilizationNombre à virgule flottante, 0-100Taux d'utilisation du journal en %
journal-uncommittedEntierMessages en attente dans le journal
journal-read-rate / journal-write-rateNombreMessages/s lus ou écrits
inputs-total / inputs-running / inputs-failedEntierNombre d'inputs configurés/actifs/en échec
throughputEntierMessages/s à l'échelle du cluster
nodes-total / nodes-unhealthyEntierNombre total de nœuds Graylog / nœuds en mauvaise santé
metricquelconque (passthrough)Accès générique à n'importe quelle métrique Dropwizard interne, nécessite --metric-name + --field
list-metrics-lldJSON LLD ZabbixPas une valeur mesurée, mais un format de découverte pour le Low-Level Discovery (voir ci-dessous)

Particularité : list-metrics-lld — Low-Level Discovery Zabbix

Au lieu de se contenter, comme pour Icinga2, d'afficher une simple liste texte pour une recherche manuelle, ce mode fournit le format JSON LLD natif de Zabbix : 

{"data": [{"{#METRICNAME}": "org.graylog2.journal.append.1-sec-rate"}, ...]}

Cela peut être intégré directement comme règle de découverte dans Zabbix, afin de générer automatiquement des prototypes d'item pour toutes les métriques trouvées — une fonctionnalité Zabbix qui n'a pas d'équivalent direct chez Icinga2.

lbstatus : le même correctif que pour Icinga2

/system/lbstatus répond avec Content-Type: text/plain et le statut dans le code de statut HTTP lui-même (200/429/503), pas dans le corps. Le script interroge ici spécifiquement avec Accept: */* (et non application/json comme pour les autres modes) — sinon Graylog renvoie 406 Not Acceptable. Cette erreur a été trouvée lors du test en conditions réelles de la variante Icinga2, et est ici correctement implémentée dès le départ.

Authentification

Identique à la variante Icinga2 : token API Graylog via authentification HTTP Basic, le token comme nom d'utilisateur, la chaîne littérale "token" comme mot de passe.

Le rôle Reader ne suffit PAS pour metric/list-metrics-lld Confirmé en conditions réelles (voir Vérification en conditions réelles) : avec le seul rôle Reader, les points de terminaison /system/metrics/* renvoient 403 Not authorized. Les 12 autres modes fonctionnent sans problème avec Reader. Pour les deux modes de métriques, ajouter en plus quatre permissions sur l'utilisateur : 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'

Configuration UserParameter

Fichier userparameter_graylog.conf dans ce dossier, à déposer sur l'agent Zabbix (pas sur le serveur) : 

UserParameter=graylog.lbstatus,python3 /pfad/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode lbstatus
UserParameter=graylog.journal.utilization,python3 /pfad/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode journal-utilization
...
UserParameter=graylog.metric[*],python3 /pfad/check_graylog_zabbix.py --url http://<graylog>:9000/api --token <token> --mode metric --metric-name $1 --field $2
Items paramétrés avec [*] La dernière ligne montre le mécanisme de Zabbix pour les items paramétrés : la clé d'item Zabbix graylog.metric[jvm.memory.heap.usage,value] transmet jvm.memory.heap.usage comme $1 et value comme $2 à la commande UserParameter. Testé en conditions réelles, fonctionne comme prévu (voir ci-dessous).

Après chaque modification de ce fichier, l'agent Zabbix doit être rechargé (systemctl restart zabbix-agent2 ou zabbix-agentd selon la version).

Installation standard (environnement Zabbix réel)

En partant d'une installation standard de serveur et d'agent Zabbix déjà en fonctionnement (installation par paquet, pas la configuration de test Docker).

  1. Créer un utilisateur Reader dans Graylog et générer un token API — procédure identique à la variante Icinga2, voir ../icinga/INSTALL.md, étapes 1-3 (seule l'étape 2, les permissions de métriques, est également nécessaire ici si metric/list-metrics-lld doivent être utilisés).
  2. Copier le script sur l'hôte de l'agent Zabbix (pas sur le serveur — c'est l'agent qui exécute les commandes UserParameter, pas le serveur) : 
    cp scripts/check_graylog_zabbix.py /usr/lib/zabbix/externalscripts/
chmod +x /usr/lib/zabbix/externalscripts/check_graylog_zabbix.py
    Python 3 et python3-requests doivent être installés sur cet hôte.
  3. Déployer le fichier UserParameter, en adaptant l'URL/le token à chaque ligne : 
    cp userparameter_graylog.conf /etc/zabbix/zabbix_agent2.d/
systemctl restart zabbix-agent2
  4. Avant la configuration dans Zabbix, tester que l'agent fournit lui-même les valeurs correctement : 
    zabbix_agent2 -t graylog.journal.utilization
# Erwartete Ausgabe: graylog.journal.utilization  [s|<Zahl>]
# "s" = success. Bei "e" (error) stimmt Pfad/Token/Netzwerk nicht.
  5. Créer l'hôte dans Zabbix (interface web : Data collection → Hosts → Create host), faire pointer l'interface agent vers l'IP de l'hôte agent.
  6. Créer les items pour chaque valeur souhaitée — type "Zabbix agent", clé exactement comme dans le fichier UserParameter (par ex. graylog.journal.utilization), choisir le type de valeur approprié (numeric float pour les pourcentages, numeric unsigned pour les compteurs, character pour les chaînes de statut comme cluster-status).
  7. Créer les triggers pour les seuils, par ex. : 
    last(/<host>/graylog.journal.utilization)>80   -> Warning
last(/<host>/graylog.journal.utilization)>95   -> High
last(/<host>/graylog.cluster.status)<>"green"  -> Warning
  8. Après un intervalle de poll (delay de l'item, par ex. 30s), vérifier les valeurs d'item et l'état des triggers dans l'interface Zabbix sous Monitoring → Latest data ou Monitoring → Problems.
À adapter avant la mise en production
  • Les seuils de trigger proposés ici (80 %/95 %) ont été établis contre une instance de test vide, non validés contre votre volume de messages réel.
  • nodes-unhealthy seul ne détecte pas de façon fiable une panne complète d'un nœud (un nœud manquant disparaît simplement de la liste des nœuds) — vérifier en plus nodes-total par rapport au nombre de nœuds connu via un trigger (last(...)<<nombre attendu>).
  • TLS / certificats auto-signés : ajouter --insecure comme argument supplémentaire dans la ligne UserParameter si nécessaire.

Vérification en conditions réelles (2026-07-24)

Comme pour la variante Icinga2, non seulement construit d'après la documentation, mais testé contre un véritable environnement Zabbix mis en place via Docker Compose (Zabbix Server + Zabbix Web + PostgreSQL + Zabbix Agent2, images officielles Zabbix, tag :latest résolu au moment du test en Zabbix 7.4.12) sur la même VM de test que Graylog.

Correction : ici aussi, test initial effectué par erreur contre Graylog 6.1 Même discordance de version que pour la variante Icinga2 (voir sa Vérification en conditions réelles) : le premier test de ce script (test agent, création d'items/triggers) a tourné contre graylog/graylog:6.1, pas contre la version correspondant à la spécification OpenAPI. Après la question de Raphael, la pile de test Graylog a été basculée vers graylog/graylog:7.1.3 (+ mongo:7.0, exigé impérativement par 7.1.3) et le test Zabbix complet a été répété — test agent, nouveau token API, valeurs d'item, évaluation des triggers. Résultat : identique, aucun des 15 modes ne s'est comporté différemment entre 6.1 et 7.1.3.

Étapes de test et résultats

  1. Les 15 modes exécutés individuellement contre la véritable API Graylog (pas via Zabbix, directement via python3 check_graylog_zabbix.py) — tous ont renvoyé des valeurs brutes correctes et plausibles, par ex. journal-utilization: 0.0, cluster-status: yellow, nodes-total: 1.
  2. Conteneur agent Zabbix mis en place, fichier UserParameter intégré, Python3 + requests installés après coup dans le conteneur (l'image officielle de l'agent Zabbix ne les inclut pas — exactement comme précédemment pour le conteneur Icinga2).
  3. Test côté agent (zabbix_agent2 -t <key>) confirmant le succès pour toutes les clés testées : 
    graylog.journal.utilization                   [s|0.0]
graylog.lbstatus                              [s|ALIVE]
graylog.cluster.status                        [s|yellow]
graylog.throughput                            [s|0]
graylog.nodes.total                           [s|1]
graylog.metric[jvm.memory.heap.usage,value]   [s|0.1861647253430262]
    La dernière entrée confirme également que la syntaxe paramétrée [*] fonctionne comme documenté.
  4. Cycle serveur complet confirmé via l'API Zabbix : un hôte, deux items (graylog.journal.utilization, graylog.cluster.status) et un trigger (last(...cluster.status)<>"green") créés en direct via l'API JSON-RPC de Zabbix. Interrogés depuis le serveur lui-même après un cycle de poll (pas depuis le test agent, mais les valeurs réellement stockées par le serveur) : 
    Item "Graylog Journal Utilization": lastvalue = "0"
Item "Graylog Cluster Status":      lastvalue = "yellow"
Trigger "Graylog indexer cluster not green on {HOST.NAME}": value = "1"  (PROBLEM)

    (Ce passage encore contre Graylog 6.1, avant la correction de version.)

  5. Nouveau test contre Graylog 7.1.3 : nouvel utilisateur Reader + token générés sur l'instance 7.1.3 fraîchement installée, fichier UserParameter et les deux items/le trigger créés basculés sur le nouveau token. Test agent à nouveau réussi (graylog.cluster.status [s|green] immédiatement après le basculement, puis de nouveau yellow plus tard dans le test – fluctuation normale pour un OpenSearch à nœud unique fraîchement installé, pas une erreur). Le trigger est resté correctement en "PROBLEM" dans les deux états, dès que la valeur n'était pas exactement "green" – confirme que la réactivité en conditions réelles de l'ensemble du cycle fonctionne également sans changement en 7.1.3.
Concrètement, cela signifie Le trigger est effectivement déclenché (état "PROBLEM"), car cluster-status = "yellow" et non "green" — exactement le comportement attendu. Cela confirme le cycle complet : le serveur Zabbix interroge l'agent → l'agent exécute la commande UserParameter → le script interroge la véritable API Graylog → la valeur brute remonte vers le serveur → elle est stockée comme item → l'expression du trigger est évaluée correctement. Pas seulement « censé fonctionner d'après la doc », mais réellement mis à l'épreuve.

Différence avec la vérification Icinga2 : aucun nouveau test des permissions API

La lacune de permissions des métriques (le rôle Reader ne suffit pas pour /system/metrics/*) avait déjà été trouvée et corrigée lors de la variante Icinga2 contre la même instance Graylog (l'utilisateur de test avec les permissions ajoutées est le même) — ici, seul le mode metric lui-même a été retesté, sans réexaminer la question des permissions depuis le début.

Points ouverts

  • Seules 2 des 15 clés d'item ont été associées à un véritable trigger dans Zabbix (journal.utilization, cluster.status) — les autres n'ont été testées qu'au niveau de l'agent (zabbix_agent2 -t), sans triggers propres câblés dans Zabbix
  • list-metrics-lld n'a été testé que comme sortie brute, sans être réellement intégré comme règle de découverte dans Zabbix (aucun prototype d'item généré automatiquement n'a été vérifié)
  • Testé contre une instance Graylog vide et fraîche, sans charge de messages réelle — les seuils de trigger ne sont pas validés pour une exploitation en production
  • Scénario multi-nœuds (nodes-total > 1) non testé, l'environnement de test ne comportant qu'un seul nœud Graylog
