Ziel

Icinga2 soll die wichtigsten Graylog-Zustände regelmäßig über dessen REST API abfragen, nicht nur "läuft der Prozess" prüfen. Ein Graylog-Server kann technisch laufen und trotzdem in einem Zustand sein, der bald zu Datenverlust führt (z. B. ein voller Message-Journal) – genau solche Zustände sollen früh sichtbar werden.

Funktionsweise: Nagios/Icinga2-Plugin-Konventionen

Icinga2 versteht kein eigenes Plugin-Format – es ruft ein beliebiges Kommandozeilenprogramm auf und interpretiert Exit-Code und Standardausgabe nach einem seit Nagios etablierten Standard (dem "Monitoring Plugins API").

Exit-CodeBedeutung
0OK
1WARNING
2CRITICAL
3UNKNOWN (z. B. Verbindungsfehler, unerwartete API-Antwort)

Die erste Ausgabezeile ist die für Icinga sichtbare Statusmeldung. Optional folgt nach einem | (Pipe) Performance-Data im Format label=wert;warn;crit;min;max – das sind die Werte, die Icinga/Grafana später für Graphen nutzen, ohne die Textmeldung parsen zu müssen. check_graylog.py folgt exakt diesem Schema: 

GRAYLOG WARNING - journal utilization is 82.3% (14200 uncommitted entries) | utilization=82.3%;80.0;95.0;0;100 uncommitted_entries=14200;;;0 read_msgs_per_sec=310;;;0 write_msgs_per_sec=340;;;0

Icinga liest daraus: Status = WARNING, Textmeldung, und vier Messwerte für die Graphen.

Ein Skript, acht Modi statt acht Einzelskripte Auth-Handling, HTTP-Fehlerbehandlung und Perfdata-Formatierung bleiben so an einer Stelle, statt achtmal dupliziert zu werden.

Die acht Modi im Detail

1. lbstatus

EndpointGET /api/system/lbstatus
ZweckGraylogs eigener, aggregierter Gesundheitsstatus, gedacht für Load-Balancer-Healthchecks. Günstigste, schnellste Prüfung.
AntwortKlartext ALIVE, THROTTLED oder DEAD
MappingALIVE→OK, THROTTLED→WARNING (Graylog drosselt bewusst die Annahme neuer Nachrichten, meist weil Indexer/Journal unter Druck stehen), DEAD→CRITICAL

2. cluster

EndpointGET /api/system/indexer/cluster/health
ZweckZustand des dahinterliegenden Elasticsearch-/OpenSearch-Clusters, auf dem Graylog seine Indizes ablegt. Graylog selbst kann laufen, während Suche/Indizierung bereits gestört ist.
AntwortJSON mit status (green/yellow/red) und einem shards-Objekt
Mappinggreen→OK, yellow→WARNING (meist fehlende Replikat-Shards – in einem Single-Node-Homelab-Setup dauerhaft normal), red→CRITICAL (Primär-Shards fehlen, echter Datenverlust-Zustand)

3. journal

EndpointGET /api/system/journal
ZweckDer eigentliche Frühwarn-Indikator. Graylog schreibt eingehende Nachrichten zunächst in einen lokalen Journal (Kafka-artiges Append-only-Log) und erst von dort in den Indexer. Kommt der Indexer nicht hinterher, wächst der Journal, statt dass Nachrichten sofort verloren gehen – aber nur bis zur konfigurierten Journal-Größe.
AntwortJSON mit u. a. utilization_ratio (0.0–1.0), uncommitted_journal_entries, append_events_per_second, read_events_per_second, enabled
SchwellenwerteDefault WARNING ab 80 %, CRITICAL ab 95 % Auslastung (--warning/--critical überschreibbar). Journal laut API deaktiviert → OK mit Hinweistext.
Warum das der wichtigste Check ist cluster und lbstatus können beide noch grün sein, während der Journal bereits deutlich voller wird – das ist das erste messbare Symptom, bevor überhaupt etwas rot wird.

4. inputs

EndpointGET /api/system/inputstates
ZweckPrüft jeden konfigurierten Input (z. B. Syslog-UDP-Listener, GELF-Input) einzeln auf seinen Laufzustand – ein einzelner abgestürzter Input wird von cluster/lbstatus nicht erkannt.
AntwortJSON-Liste mit state pro Input (RUNNING, FAILED, STOPPED, ...) und Titel
MappingAlles RUNNING→OK. Irgendein Input nicht RUNNING→CRITICAL, mit Auflistung. Keine Inputs konfiguriert→WARNING.

5. throughput

EndpointGET /api/system/throughput
ZweckCluster-weite Nachrichten/Sekunde – primär für Trend/Graphen, sekundär als Ausfall-Indikator ("Ingestion komplett zum Stillstand gekommen").
SchwellenwerteStandardmäßig keine – 0 Nachrichten/s ist in einem ruhigen Homelab normal. Werden --warning/--critical gesetzt, wirken sie als Untergrenze (Wert darunter ist das Problem).

6. nodes neu, 2026-07-23

EndpointGET /api/cluster
ZweckBeantwortet "sind wirklich alle Graylog-Knoten erreichbar" – die fünf Modi oben werden alle von genau dem einen Knoten beantwortet, den die Anfrage zufällig trifft, nicht vom gesamten Cluster. Ein zweiter Knoten kann dabei längst weg sein, ohne dass lbstatus/cluster/journal das bemerken.
AntwortJSON-Dictionary node_id → SystemOverviewResponse (u. a. hostname, lb_status, is_processing, lifecycle) – ein Eintrag pro Knoten, der geantwortet hat
MappingJeder Knoten mit lb_status != "ALIVE" oder is_processing = false → CRITICAL. Optional --expected-nodes N: weniger Knoten als erwartet in der Antwort → CRITICAL (der Fall, wenn ein Knoten komplett ausfällt und daher gar nicht erst im Dictionary auftaucht).

7. metric neu, 2026-07-23

EndpointGET /api/system/metrics/{metricName}
ZweckGenerischer Zugriff auf eine einzelne von Graylogs internen Dropwizard-Metriken – JVM-Heap, Garbage Collection, CPU, Ring-Buffer-Auslastung (Input/Process/Output), Pipeline-Performance, Thread-Pools. Ein Modus statt sieben, weil Graylog keinen Wildcard-Endpoint für Metrik-Familien anbietet (siehe ChatGPT-Vorlage: Bewertung).
Parameter--metric-name (Pflicht, exakter Name, z. B. jvm.memory.heap.usage), --field (Punkt-Pfad in das JSON hinein, Default value), --warning/--critical
MappingWert ≥ --critical → CRITICAL, ≥ --warning → WARNING, sonst OK. Fehlt --field in der Antwort → UNKNOWN.
Einzige Stelle im Skript ohne Spezifikations-Garantie Das MetricsSummaryResponse/com.codahale.metrics.Metric-Schema ist in der OpenAPI-Spezifikation leer ({}) – Dropwizard-Metriken serialisieren je nach Typ unterschiedlich (Gauge: value, Counter: count, Meter/Timer: verschachtelte rate/time-Objekte), und das ist selbst in der Spezifikation nicht dokumentiert. Der --field-Pfad ist deshalb ein Best-Effort-Parameter, keine bestätigte Struktur – vor dem Produktiveinsatz mit list-metrics (unten) und einem manuellen curl gegen die echte Instanz verifizieren.

8. list-metrics neu, 2026-07-23

EndpointGET /api/system/metrics/names
ZweckKein echter Check, sondern ein Entdeckungs-Werkzeug: listet alle auf der Instanz verfügbaren Metrik-Namen (optional gefiltert mit --filter), damit man den exakten Namen für --mode metric --metric-name ... findet, statt ihn zu erraten.
MappingImmer OK – reine Auflistung, keine Bewertung.

Authentifizierung

Graylogs REST API akzeptiert API-Tokens als HTTP Basic Auth, wobei das Token selbst der Benutzername ist und als Passwort der feste, wörtliche String "token" übergeben wird (kein Platzhalter – das ist tatsächlich so von Graylog spezifiziert). Zusätzlich setzt das Skript bei jedem Request den Header X-Requested-By mit (CSRF-Schutz, den Graylogs API bei manchen Operationen verlangt).

Least Privilege Token an einen eigenen Graylog-Benutzer mit Reader-Rolle binden, nicht an einen Admin-Account – das Token liegt auf dem Icinga2-Host.
Live bestätigt: Reader-Rolle reicht NICHT für metric/list-metrics Beim Live-Test (siehe Live-Verifikation) hat sich gezeigt: mit reiner Reader-Rolle liefern /system/metrics/*-Endpunkte 403 Not authorized – lbstatus, cluster, journal, inputs, throughput und nodes funktionieren mit Reader problemlos, aber die beiden Metrik-Modi brauchen zusätzlich vier explizite Permissions am Benutzer: metrics:read, metrics:allkeys, metrics:readall, metrics:readhistory. Diese lassen sich per API direkt auf den Benutzer setzen (zusätzlich zur Reader-Rolle, nicht als Ersatz): 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'
Die <user-id> ist Graylogs interne MongoDB-ObjectId, nicht der Benutzername – abrufbar über GET /api/users/<username> (Feld id). Wer nur die sechs Basis-Checks braucht (kein metric/list-metrics), kann diesen Schritt überspringen.

Konfiguration in Icinga2

Zwei Dateien decken das ab:

  • commands.conf.example – definiert das CheckCommand-Objekt, das die Icinga2-DSL-Variablen ($graylog_url$, $graylog_token$, ...) auf die CLI-Argumente von check_graylog.py abbildet
  • services-graylog.conf.example – fünf apply Service-Regeln (eine pro Modus), die auf jeden Host mit gesetztem vars.graylog_url greifen

Praktisch: check_graylog.py landet auf dem Icinga2-Host unter PluginDir (typisch /usr/lib/nagios/plugins/), beide .conf.example-Dateien werden kopiert (Endung .example entfernen) und die Platzhalter-Werte (graylog_url, graylog_token, Ziel-IP) angepasst.

Verwendete Quellen

Wichtig für die Einordnung In dieser Session wurde keine Websuche und kein Live-Abruf der offiziellen Graylog-Dokumentation durchgeführt.

Das Skript basiert auf trainiertem Wissen über:

  • Graylogs REST-API-Struktur (offizielle Doku unter docs.graylog.org, insbesondere die Endpunkte unter /api/system/*) – aus Trainingsdaten, nicht live nachgeschlagen
  • Die "Nagios Plugin Development Guidelines" (Monitoring Plugins Project, monitoring-plugins.org) für Exit-Codes und Performance-Data-Format – ebenfalls aus Trainingsdaten
  • Allgemeines Wissen über Icinga2s DSL (CheckCommand, apply Service)

Das heißt konkret: Die verwendeten Endpunkt-Pfade und JSON-Feldnamen (utilization_ratio, uncommitted_journal_entries, shards, ...) entsprechen dem Stand, der mir aus Training bekannt ist – sie können sich zwischen Graylog-Versionen leicht unterscheiden (Graylog ändert REST-API-Details gelegentlich zwischen Major-Versionen).

Vor Produktiveinsatz verifizieren Jeden Modus einmal von Hand gegen die tatsächlich laufende Graylog-Version testen, z. B.: 
curl -u <token>:token https://<graylog>:9000/api/system/journal
und die JSON-Struktur mit dem im Skript erwarteten Format vergleichen.

Update: Dieser Abgleich wurde inzwischen für die API-Struktur nachgeholt – nicht per Websuche, sondern weil Raphael mir einen echten OpenAPI-Export seiner Graylog-Instanz zur Verfügung gestellt hat. Ergebnisse und zwei dabei gefundene Fehler: OpenAPI-Abgleich (2026-07-23).

OpenAPI-Abgleich (2026-07-23)

Raphael hat mir einen Export der Graylog-REST-API-Spezifikation zur Verfügung gestellt: openapi.json (~1,1 MB, OpenAPI 3.1.0, 515 Endpunkte, Graylog-Version 7.1.3+c34604d), abgelegt direkt in diesem Ordner. Damit ließ sich die in Verwendete Quellen angemahnte Verifikation tatsächlich durchführen – nicht mehr nur als offener Punkt, sondern als echter Abgleich von Annahme gegen Spezifikation.

Alle fünf vom Plugin genutzten Endpunkte existieren exakt unter den erwarteten Pfaden. Ergebnis pro Modus:

ModusEndpointErgebnis
lbstatus /system/lbstatus Fehler gefunden & behoben
journal /system/journal Fehler gefunden & behoben
cluster /system/indexer/cluster/health bestätigt korrekt
inputs /system/inputstates bestätigt korrekt
throughput /system/throughput bestätigt korrekt

Fehler 1: lbstatus kommuniziert über den HTTP-Statuscode, nicht über den Body

Die Annahme war, Graylog liefert bei /system/lbstatus immer HTTP 200 und den eigentlichen Status (ALIVE/THROTTLED/DEAD) als Klartext im Response-Body. Laut Spezifikation stimmt das nicht: der Zustand steckt im HTTP-Statuscode selbst – 200=ALIVE, 429=THROTTLED, 503=DEAD.

Das war ein echter Bug: die gemeinsame api_get()-Hilfsfunktion des Skripts behandelte jeden Nicht-200-Code als Verbindungsfehler (UNKNOWN) – THROTTLED und DEAD wären also nie als solche erkannt worden, sondern immer nur als "kann Graylog nicht erreichen" gemeldet. check_lbstatus() macht jetzt seinen eigenen Request statt über api_get() zu gehen und wertet den Statuscode direkt aus.

Fehler 2: journal hat kein Feld utilization_ratio

Die komplette Warn/Krit-Schwellenwert-Logik von check_journal() beruhte auf einem Feld utilization_ratio (0.0–1.0) in der Antwort von /system/journal. Laut JournalSummaryResponse-Schema in der Spezifikation existiert dieses Feld schlicht nicht. Vorhanden sind stattdessen journal_size und journal_size_limit (beide in Bytes) – die Auslastung muss selbst berechnet werden: journal_size / journal_size_limit * 100. Das Skript macht das jetzt so, mit einer Absicherung gegen Division durch Null, falls journal_size_limit einmal 0 ist.

Wichtige Einschränkung dieses Abgleichs Das war ein struktureller Abgleich (welche Felder gibt es, wie heißen sie, welchen Typ haben sie) anhand der Spezifikation – kein Laufzeit-Test mit echten Werten aus einer laufenden Instanz. Ob z. B. die Warn/Krit-Schwellenwerte im journal-Modus (80 %/95 %) bei echten Werten sinnvoll reagieren, oder ob check_lbstatus() tatsächlich einen 429er bekommt, wenn Graylog throttelt, lässt sich erst gegen eine laufende Instanz zeigen (siehe Nächste Schritte).

ChatGPT-Vorlage: Bewertung (2026-07-23)

Raphael hat mir zusätzlich original-chatgpt-proposal.txt zur Verfügung gestellt – eine Liste von zehn vorgeschlagenen Checks von ChatGPT. Abgleich jedes Vorschlags gegen die echte OpenAPI-Spezifikation (openapi.json):

VorschlagVorgeschlagener EndpointBewertung
Clusterstatus GET /api/cluster korrekt – existiert genau so, jetzt als Modus nodes umgesetzt
Node-Informationen GET /api/system/cluster/nodes Endpoint existiert – /api/cluster (oben) liefert dieselbe Information direkt mit Gesundheitsstatus pro Knoten, daher dafür verwendet statt eines zweiten Aufrufs
Journal-Auslastung GET /api/system/metrics/org.graylog2.journal.* Pfad falsch – Wildcard-Pfade existieren nicht; bereits als eigener Modus journal über den dedizierten /system/journal-Endpoint gelöst (besser als der Metrik-Umweg)
Input/Process/Output Buffer GET /api/system/metrics/org.graylog2.buffers.*.* Pfad falsch – gleiches Problem; jetzt über generischen Modus metric abrufbar, sobald die exakten Metrik-Namen per list-metrics --filter buffers ermittelt sind
Message Throughput GET /api/system/throughput korrekt – bereits als Modus throughput umgesetzt (siehe OpenAPI-Abgleich)
Inputs GET /api/system/inputs Endpoint existiert – /api/system/inputstates (bereits als Modus inputs umgesetzt) liefert zusätzlich direkt den Laufzustand pro Input, ist für einen Check die passendere Wahl
JVM Heap / GC / CPU / Pipeline / Thread Pools / Processing Rate GET /api/system/metrics/<namespace>.* Pfad falsch – gleiches Wildcard-Problem für alle sechs; jetzt einheitlich über Modus metric abrufbar

Kurzfassung: Die Metrik-Auswahl von ChatGPT ist fachlich sinnvoll und deckt echte Lücken ab, die die ursprünglichen fünf Modi hatten (v. a. Buffer-Auslastung und Multi-Node-Erreichbarkeit fehlten komplett). Die Endpoint-Syntax für alles unter /system/metrics/... ist aber nicht korrekt – Graylogs REST API kennt keine Wildcard-Pfade wie org.graylog2.journal.*. Der tatsächliche Mechanismus:

  • GET /system/metrics/{metricName} – ein exakt benannter Einzelwert
  • GET /system/metrics/namespace/{namespace} – alle Metriken unter einem Namensraum (ohne .*-Suffix)
  • POST /system/metrics/multiple – eine explizite Liste von Metrik-Namen auf einmal
  • GET /system/metrics/names – Discovery: alle verfügbaren Namen

Umgesetzt wurden die zwei spezifikations-sicheren, sofort korrekt nachbaubaren Vorschläge (nodes für Clusterstatus/Node-Info) sowie ein generischer metric-Modus plus list-metrics-Discovery-Helfer für den ganzen Rest (JVM Heap, GC, CPU, Buffer, Pipeline, Thread Pools) – siehe Die acht Modi, Punkte 6–8. Bewusst nicht für jede einzelne Metrik-Familie ein eigener hartkodierter Modus mit geratenen Feldnamen, nachdem genau das bei utilization_ratio im journal-Modus bereits einmal danebenlag (siehe OpenAPI-Abgleich) – die konkreten Metrik-Response-Formen sind in der Spezifikation nicht typisiert, ein generischer Modus ist hier ehrlicher als sieben Modi mit unbestätigten Annahmen.

Live-Verifikation (2026-07-24)

Der in OpenAPI-Abgleich beschriebene Struktur-Check wurde jetzt durch einen echten Laufzeit-Test ergänzt: eine tatsächlich laufende Graylog-Instanz plus eine tatsächlich laufende Icinga2-Instanz, beide per Docker aufgesetzt, das Plugin komplett durchgetestet und in Icinga2 scharf geschaltet.

Testszenario

Aufgebaut auf einer eigenen Test-VM (HP1-icinga01, 192.168.10.35, 8 GB RAM) im Homelab-Cluster, komplett per Docker Compose, ohne dauerhafte Systeminstallation:

KomponenteImageRolle
MongoDBmongo:7.0Graylogs Konfigurationsdatenbank
OpenSearchopensearchproject/opensearch:2.19.0Indexer/Suche (Single-Node, Security-Plugin deaktiviert)
Grayloggraylog/graylog:7.1.3Die zu testende Anwendung selbst — bewusst exakt dieselbe Version wie die für den OpenAPI-Abgleich verwendete Spezifikation (7.1.3+c34604d)
Icinga2icinga/icinga2:latest (v2.16.4)Führt das Plugin real über CheckCommand/Service aus, in einem separaten Compose-Stack
Korrektur: erster Testlauf versehentlich gegen Graylog 6.1 statt 7.x Der ursprüngliche Live-Test lief zunächst gegen graylog/graylog:6.1 – ein Versehen, da die OpenAPI-Spezifikation, gegen die vorher die Struktur abgeglichen wurde, für Graylog 7.1.3 war. Raphael hat das beim Doku-Lesen bemerkt und nachgefragt. Der komplette Live-Test (alle acht Modi, Icinga2-Integration) wurde danach gegen graylog/graylog:7.1.3 wiederholt – mit identischem Ergebnis: keiner der beiden gefundenen Bugs (lbstatus-Header, Metrics-Berechtigungen) war 6.1-spezifisch, beide Fixes gelten unverändert auch bei 7.1.3. Nebenbefund dabei: Graylog 7.1.3 verlangt mindestens MongoDB 7.0 (mit 6.0 bricht der Start mit einer expliziten Preflight-Fehlermeldung ab) – reine Infrastruktur-Voraussetzung für den Testaufbau, keine Änderung an der REST-API selbst.
Stolperstein beim Aufbau: OpenSearch 2.12+ verlangt ein Admin-Passwort, auch wenn Security deaktiviert ist plugins.security.disabled=true allein reicht seit OpenSearch 2.12 nicht mehr – der Container bricht ohne OPENSEARCH_INITIAL_ADMIN_PASSWORD beim Start ab (Crash-Loop). Relevant nur für den Aufbau einer Testumgebung wie dieser, nicht für den Plugin-Code selbst.

Für den Icinga2-Test-Container: Das Image basiert auf Debian 13, enthält aber standardmäßig kein Python 3 – musste per apt-get install python3 python3-requests nachinstalliert werden, bevor check_graylog.py überhaupt ausführbar war. In einer regulären Debian/Ubuntu-Icinga2-Installation (kein Container) ist das in aller Regel bereits vorhanden.

Beide Bugs bei 7.1.3 identisch bestätigt Der komplette Testlauf wurde nach Entdeckung des Versions-Mismatches (siehe oben) gegen die korrekte Version wiederholt. Ergebnis: keiner der beiden gefundenen Bugs war 6.1-spezifisch – beide Fixes (Accept-Header bei lbstatus, Metrics-Permissions) sind bei 7.1.3 unverändert nötig und wirksam.

Bug 1: lbstatus lieferte HTTP 406 statt der Statusauskunft

Live-Ergebnis vor dem Fix: GRAYLOG UNKNOWN - load balancer status is HTTP 406. Ursache: /system/lbstatus antwortet mit Content-Type: text/plain, das Skript sandte aber für alle Endpunkte pauschal Accept: application/json – Graylog verweigert die Antwort dann mit 406 Not Acceptable, statt einfach Klartext zu liefern. Fix: für diesen einen Endpunkt Accept: */* statt application/json.

Warum das im OpenAPI-Abgleich nicht auffiel Der frühere Struktur-Test (siehe OpenAPI-Abgleich) hat nur die Spezifikation gelesen, nie eine echte HTTP-Anfrage gestellt – ein Accept-Header-Konflikt zeigt sich naturgemäß erst im echten Request/Response-Zyklus. Genau das ist der Unterschied zwischen Struktur-Verifikation und Laufzeit-Verifikation.

Bug 2 (eigentlich: Rechte-Lücke): metric/list-metrics mit reinem Reader-Token

Live-Ergebnis vor dem Fix: GRAYLOG UNKNOWN - .../system/metrics/names returned HTTP 403: Not authorized. Kein Bug im Skript, sondern eine Berechtigungslücke der Reader-Rolle in Graylog – Details und Fix siehe Authentifizierung weiter oben.

Einrichtung für den Produktiveinsatz

Diese Anleitung geht von einer echten Graylog- und Icinga2-Installation aus (Paket-/Systeminstallation, kein Docker-Testaufbau wie oben) – für eine bereits laufende Umgebung wie eure.

  1. Reader-Benutzer in Graylog anlegen (Web-UI: System → Users → Create User, Rolle "Reader"), oder per API: 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users" \
  -d '{"username":"icinga-monitoring","password":"<starkes-passwort>",
       "first_name":"Icinga","last_name":"Monitoring","email":"icinga@example.org",
       "roles":["Reader"],"permissions":[]}'
  2. Nur falls metric/list-metrics genutzt werden sollen: die vier Metrics-Permissions nachrüsten (siehe Authentifizierung für den genauen Befehl und die User-ID-Ermittlung).
  3. API-Token für diesen Benutzer erzeugen: 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users/<user-id>/tokens/icinga-check"
    Antwort enthält das eigentliche Token im Feld token – das ist der Wert für graylog_token in Icinga2, nicht das Benutzerpasswort.
  4. check_graylog.py auf den Icinga2-Host kopieren, z. B. nach /usr/lib/nagios/plugins/check_graylog.py. Python 3 + das Paket requests müssen dort vorhanden sein (apt install python3-requests).
  5. commands.conf.example und services-graylog.conf.example aus diesem Ordner nach /etc/icinga2/conf.d/ kopieren, Endung .example entfernen.
  6. In der kopierten Services-Datei bzw. im Host-Objekt eurer Graylog-Instanz vars.graylog_url (die API-Root-URL, z. B. https://graylog.example.org:9000/api) und vars.graylog_token (das Token aus Schritt 3) setzen.
  7. Konfiguration validieren, bevor neu geladen wird: 
    icinga2 daemon -C
  8. Icinga2 neu laden/starten. Nach einem Check-Intervall die Services im Icinga-Web-Frontend prüfen, oder direkt per CLI: 
    icinga2 object list --type Service --name '<hostname>!graylog-*'
Vor dem produktiven Rollout unbedingt beachten
  • TLS: Läuft eure Graylog-Instanz auf HTTPS mit selbstsigniertem Zertifikat, vars.graylog_insecure = true setzen (oder besser: ein echtes Zertifikat hinterlegen).
  • Der journal-Modus hat Default-Schwellenwerte von 80 %/95 % – bei produktivem Nachrichtenaufkommen ggf. anpassen, die hier getesteten Werte (0 %) sagen über euer reales Aufkommen nichts aus.
  • nodes-Modus: --expected-nodes auf die tatsächliche Node-Anzahl eures Clusters setzen, sonst wird ein fehlender Node nicht zuverlässig erkannt.

Offene Punkte

  • Getestet wurde gegen eine frische, leere Graylog-Instanz ohne reale Nachrichtenlast – Schwellenwerte (journal, throughput) sind gegen echten Produktivbetrieb noch nicht validiert
  • metric/list-metrics wurden nur mit einem Beispiel (jvm.memory.heap.usage) getestet – weitere gewünschte Metriken (Buffer-Auslastung etc.) vor Nutzung einmal mit list-metrics suchen und einzeln verifizieren
  • Multi-Node-Test von nodes/--expected-nodes steht noch aus (Testumgebung hatte nur einen Graylog-Node)
