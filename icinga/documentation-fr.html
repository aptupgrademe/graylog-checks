check_graylog.py – Documentation

Plugin de vérification Icinga2 pour Graylog · Projet frère de graylog-checks/zabbix · État : juillet 2026

Plan de lecture GRAYLOG-CONCEPTS.html (un niveau au-dessus) explique en détail la signification des différentes valeurs Graylog, si Graylog est nouveau pour vous ; Les huit modes explique ce que le plugin vérifie concrètement et pourquoi ; Vérification en conditions réelles montre les résultats de test réels obtenus contre une véritable instance Graylog, avec deux bugs trouvés et corrigés à cette occasion ; Mise en place pour la production est le guide pas à pas proprement dit pour votre environnement réel. Objectif

Icinga2 doit interroger régulièrement les états les plus importants de Graylog via son API REST, et pas seulement vérifier « le processus tourne-t-il ». Un serveur Graylog peut techniquement fonctionner tout en se trouvant dans un état qui mènera bientôt à une perte de données (par exemple un journal des messages plein) – ce sont précisément ces états qui doivent devenir visibles tôt.

Fonctionnement : conventions des plugins Nagios/Icinga2

Icinga2 ne connaît pas de format de plugin qui lui soit propre – il appelle n'importe quel programme en ligne de commande et interprète le code de sortie (exit code) et la sortie standard selon une norme établie depuis Nagios (la « Monitoring Plugins API »).

Code de sortieSignification
0OK
1WARNING
2CRITICAL
3UNKNOWN (par ex. erreur de connexion, réponse API inattendue)

La première ligne de sortie est le message de statut visible par Icinga. Elle peut être suivie, en option, après un | (pipe), de données de performance (performance data) au format label=valeur;warn;crit;min;max – ce sont les valeurs qu'Icinga/Grafana utiliseront ensuite pour les graphiques, sans devoir analyser le message texte. check_graylog.py suit exactement ce schéma : 

GRAYLOG WARNING - journal utilization is 82.3% (14200 uncommitted entries) | utilization=82.3%;80.0;95.0;0;100 uncommitted_entries=14200;;;0 read_msgs_per_sec=310;;;0 write_msgs_per_sec=340;;;0

Icinga en déduit : statut = WARNING, message texte, et quatre valeurs mesurées pour les graphiques.

Un seul script, huit modes plutôt que huit scripts séparés La gestion de l'authentification, le traitement des erreurs HTTP et le formatage des perfdata restent ainsi centralisés en un seul endroit, au lieu d'être dupliqués huit fois.

Les huit modes en détail

1. lbstatus

Point de terminaisonGET /api/system/lbstatus
ObjectifÉtat de santé agrégé propre à Graylog, prévu pour les contrôles de santé (healthchecks) des load balancers. La vérification la moins coûteuse et la plus rapide.
RéponseTexte brut ALIVE, THROTTLED ou DEAD
CorrespondanceALIVE→OK, THROTTLED→WARNING (Graylog limite volontairement l'acceptation de nouveaux messages, généralement parce que l'indexeur ou le journal sont sous pression), DEAD→CRITICAL

2. cluster

Point de terminaisonGET /api/system/indexer/cluster/health
ObjectifÉtat du cluster Elasticsearch/OpenSearch sous-jacent, sur lequel Graylog stocke ses index. Graylog lui-même peut fonctionner alors que la recherche/l'indexation est déjà perturbée.
RéponseJSON avec status (green/yellow/red) et un objet shards
Correspondancegreen→OK, yellow→WARNING (généralement des shards de réplication manquants – normal en permanence dans une installation homelab à nœud unique), red→CRITICAL (des shards primaires manquent, véritable situation de perte de données)

3. journal

Point de terminaisonGET /api/system/journal
ObjectifLe véritable indicateur d'alerte précoce. Graylog écrit d'abord les messages entrants dans un journal local (un log en ajout seul, à la manière de Kafka), et ce n'est qu'ensuite qu'ils passent à l'indexeur. Si l'indexeur ne suit pas le rythme, le journal grossit au lieu que les messages soient immédiatement perdus – mais seulement jusqu'à la taille de journal configurée.
RéponseJSON contenant entre autres utilization_ratio (0.0–1.0), uncommitted_journal_entries, append_events_per_second, read_events_per_second, enabled
SeuilsPar défaut WARNING à partir de 80 %, CRITICAL à partir de 95 % d'utilisation (--warning/--critical modifiables). Si le journal est désactivé selon l'API → OK avec un message d'information.
Pourquoi c'est la vérification la plus importante cluster et lbstatus peuvent tous deux être encore au vert alors que le journal se remplit déjà nettement – c'est le premier symptôme mesurable, avant même que quoi que ce soit ne passe au rouge.

4. inputs

Point de terminaisonGET /api/system/inputstates
ObjectifVérifie individuellement l'état de fonctionnement de chaque input configuré (par ex. écouteur Syslog-UDP, input GELF) – un input planté isolément n'est pas détecté par cluster/lbstatus.
RéponseListe JSON avec state par input (RUNNING, FAILED, STOPPED, ...) et titre
CorrespondanceTout en RUNNING→OK. Un input quelconque pas en RUNNING→CRITICAL, avec la liste correspondante. Aucun input configuré→WARNING.

5. throughput

Point de terminaisonGET /api/system/throughput
ObjectifMessages/seconde à l'échelle du cluster – utilisé principalement pour les tendances/graphiques, secondairement comme indicateur de panne (« l'ingestion s'est complètement arrêtée »).
SeuilsAucun par défaut – 0 message/s est normal dans un homelab calme. Si --warning/--critical sont définis, ils agissent comme une limite inférieure (le problème est une valeur en dessous).

6. nodes nouveau, 2026-07-23

Point de terminaisonGET /api/cluster
ObjectifRépond à la question « tous les nœuds Graylog sont-ils vraiment joignables » – les cinq modes ci-dessus sont tous répondus par le seul nœud que la requête atteint par hasard, pas par l'ensemble du cluster. Un deuxième nœud peut ainsi avoir disparu depuis longtemps sans que lbstatus/cluster/journal ne le remarquent.
RéponseDictionnaire JSON node_id → SystemOverviewResponse (entre autres hostname, lb_status, is_processing, lifecycle) – une entrée par nœud ayant répondu
CorrespondanceTout nœud avec lb_status != "ALIVE" ou is_processing = false → CRITICAL. En option --expected-nodes N : moins de nœuds que prévu dans la réponse → CRITICAL (le cas où un nœud tombe complètement en panne et n'apparaît donc même pas dans le dictionnaire).

7. metric nouveau, 2026-07-23

Point de terminaisonGET /api/system/metrics/{metricName}
ObjectifAccès générique à l'une des métriques internes Dropwizard de Graylog – tas JVM (heap), garbage collection, CPU, taux d'utilisation des ring buffers (Input/Process/Output), performance des pipelines, pools de threads. Un seul mode plutôt que sept, car Graylog ne propose pas de point de terminaison générique (wildcard) pour les familles de métriques (voir Modèle ChatGPT : évaluation).
Paramètres--metric-name (obligatoire, nom exact, par ex. jvm.memory.heap.usage), --field (chemin en notation pointée dans le JSON, valeur par défaut value), --warning/--critical
CorrespondanceValeur ≥ --critical → CRITICAL, ≥ --warning → WARNING, sinon OK. Si --field est absent de la réponse → UNKNOWN.
Le seul endroit du script sans garantie de spécification Le schéma MetricsSummaryResponse/com.codahale.metrics.Metric est vide ({}) dans la spécification OpenAPI – les métriques Dropwizard se sérialisent différemment selon leur type (Gauge : value, Counter : count, Meter/Timer : objets rate/time imbriqués), et ce n'est même pas documenté dans la spécification elle-même. Le chemin --field est donc un paramètre au mieux (best-effort), pas une structure confirmée – à vérifier avant la mise en production avec list-metrics (ci-dessous) et un curl manuel contre l'instance réelle.

8. list-metrics nouveau, 2026-07-23

Point de terminaisonGET /api/system/metrics/names
ObjectifCe n'est pas une véritable vérification, mais un outil de découverte : liste tous les noms de métriques disponibles sur l'instance (filtrables en option avec --filter), afin de trouver le nom exact pour --mode metric --metric-name ... plutôt que de le deviner.
CorrespondanceToujours OK – simple listage, sans évaluation.

Authentification

L'API REST de Graylog accepte les jetons API (tokens) via l'authentification HTTP Basic Auth, le token lui-même servant de nom d'utilisateur, tandis que le mot de passe transmis est la chaîne littérale fixe "token" (ce n'est pas un espace réservé – c'est réellement ainsi que Graylog le spécifie). Le script ajoute en outre l'en-tête X-Requested-By à chaque requête (protection CSRF exigée par l'API de Graylog pour certaines opérations).

Principe du moindre privilège Associer le token à un utilisateur Graylog dédié avec le rôle Reader, pas à un compte administrateur – le token réside sur l'hôte Icinga2.
Confirmé en conditions réelles : le rôle Reader ne suffit PAS pour metric/list-metrics Le test en conditions réelles (voir Vérification en conditions réelles) a montré que : avec le seul rôle Reader, les points de terminaison /system/metrics/* renvoient 403 Not authorized – lbstatus, cluster, journal, inputs, throughput et nodes fonctionnent sans problème avec Reader, mais les deux modes de métriques nécessitent en plus quatre permissions explicites sur l'utilisateur : metrics:read, metrics:allkeys, metrics:readall, metrics:readhistory. Celles-ci peuvent être définies directement sur l'utilisateur via l'API (en complément du rôle Reader, pas en remplacement) : 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'
<user-id> est l'ObjectId MongoDB interne de Graylog, pas le nom d'utilisateur – récupérable via GET /api/users/<username> (champ id). Quiconque n'a besoin que des six vérifications de base (pas de metric/list-metrics) peut sauter cette étape.

Configuration dans Icinga2

Deux fichiers couvrent cela :

  • commands.conf.example – définit l'objet CheckCommand qui fait correspondre les variables du DSL Icinga2 ($graylog_url$, $graylog_token$, ...) aux arguments CLI de check_graylog.py
  • services-graylog.conf.example – cinq règles apply Service (une par mode), qui s'appliquent à chaque Host pour lequel vars.graylog_url est défini

En pratique : check_graylog.py est déposé sur l'hôte Icinga2 dans PluginDir (typiquement /usr/lib/nagios/plugins/), les deux fichiers .conf.example sont copiés (en retirant l'extension .example) et les valeurs d'espace réservé (graylog_url, graylog_token, IP cible) sont adaptées.

Sources utilisées

Important pour la mise en contexte Dans cette session, aucune recherche web ni aucun accès en direct à la documentation officielle de Graylog n'a été effectué.

Le script s'appuie sur des connaissances acquises à l'entraînement concernant :

  • La structure de l'API REST de Graylog (documentation officielle sur docs.graylog.org, en particulier les points de terminaison sous /api/system/*) – provenant des données d'entraînement, non consultées en direct
  • Les « Nagios Plugin Development Guidelines » (Monitoring Plugins Project, monitoring-plugins.org) pour les codes de sortie et le format des données de performance – également issues des données d'entraînement
  • Des connaissances générales sur le DSL d'Icinga2 (CheckCommand, apply Service)

Concrètement, cela signifie : les chemins de points de terminaison et les noms de champs JSON utilisés (utilization_ratio, uncommitted_journal_entries, shards, ...) correspondent à l'état que je connais grâce à l'entraînement – ils peuvent légèrement différer d'une version de Graylog à l'autre (Graylog modifie parfois des détails de son API REST entre versions majeures).

Vérifier avant la mise en production Tester chaque mode une fois manuellement contre la version de Graylog réellement en cours d'exécution, par ex. : 
curl -u <token>:token https://<graylog>:9000/api/system/journal
et comparer la structure JSON avec le format attendu par le script.

Mise à jour : cette vérification a depuis été effectuée pour la structure de l'API – non pas par recherche web, mais parce que Raphael m'a fourni un véritable export OpenAPI de son instance Graylog. Résultats et deux erreurs trouvées à cette occasion : Comparaison OpenAPI (2026-07-23).

Comparaison OpenAPI (2026-07-23)

Raphael m'a fourni un export de la spécification de l'API REST de Graylog : openapi.json (~1,1 Mo, OpenAPI 3.1.0, 515 points de terminaison, version Graylog 7.1.3+c34604d), déposé directement dans ce dossier. Cela a permis d'effectuer réellement la vérification réclamée dans Sources utilisées – non plus seulement comme un point ouvert, mais comme une véritable comparaison entre hypothèse et spécification.

Les cinq points de terminaison utilisés par le plugin existent exactement aux chemins attendus. Résultat par mode :

ModePoint de terminaisonRésultat
lbstatus /system/lbstatus Erreur trouvée & corrigée
journal /system/journal Erreur trouvée & corrigée
cluster /system/indexer/cluster/health confirmé correct
inputs /system/inputstates confirmé correct
throughput /system/throughput confirmé correct

Erreur 1 : lbstatus communique via le code de statut HTTP, pas via le corps

L'hypothèse était que Graylog renvoie toujours HTTP 200 pour /system/lbstatus, avec le statut proprement dit (ALIVE/THROTTLED/DEAD) en texte brut dans le corps de la réponse. Selon la spécification, ce n'est pas exact : l'état se trouve dans le code de statut HTTP lui-même – 200=ALIVE, 429=THROTTLED, 503=DEAD.

C'était un véritable bug : la fonction utilitaire commune api_get() du script traitait tout code différent de 200 comme une erreur de connexion (UNKNOWN) – THROTTLED et DEAD n'auraient donc jamais été reconnus comme tels, mais toujours signalés comme « impossible de joindre Graylog ». check_lbstatus() effectue désormais sa propre requête au lieu de passer par api_get(), et évalue directement le code de statut.

Erreur 2 : journal n'a pas de champ utilization_ratio

Toute la logique des seuils warning/critical de check_journal() reposait sur un champ utilization_ratio (0.0–1.0) dans la réponse de /system/journal. Selon le schéma JournalSummaryResponse de la spécification, ce champ n'existe tout simplement pas. Ce qui existe à la place, ce sont journal_size et journal_size_limit (tous deux en octets) – le taux d'utilisation doit être calculé soi-même : journal_size / journal_size_limit * 100. Le script procède désormais ainsi, avec une protection contre la division par zéro au cas où journal_size_limit vaudrait 0.

Limite importante de cette comparaison Il s'agissait d'une comparaison structurelle (quels champs existent, comment s'appellent-ils, quel type ont-ils) basée sur la spécification – pas d'un test en conditions réelles avec des valeurs issues d'une instance en fonctionnement. Savoir si, par exemple, les seuils warning/critical du mode journal (80 %/95 %) réagissent de façon pertinente face à des valeurs réelles, ou si check_lbstatus() reçoit effectivement un code 429 lorsque Graylog limite le débit, ne peut être démontré que contre une instance en cours d'exécution (voir Prochaines étapes).

Modèle ChatGPT : évaluation (2026-07-23)

Raphael m'a également fourni original-chatgpt-proposal.txt – une liste de dix vérifications proposées par ChatGPT. Comparaison de chaque proposition avec la véritable spécification OpenAPI (openapi.json) :

PropositionPoint de terminaison proposéÉvaluation
État du cluster GET /api/cluster correct – existe exactement ainsi, désormais implémenté comme mode nodes
Informations sur les nœuds GET /api/system/cluster/nodes le point de terminaison existe – /api/cluster (ci-dessus) fournit directement la même information avec le statut de santé par nœud, donc utilisé à sa place plutôt qu'un second appel
Utilisation du journal GET /api/system/metrics/org.graylog2.journal.* Chemin incorrect – les chemins avec caractère générique n'existent pas ; déjà résolu par un mode dédié journal via le point de terminaison /system/journal (meilleur que le détour par les métriques)
Buffers Input/Process/Output GET /api/system/metrics/org.graylog2.buffers.*.* Chemin incorrect – même problème ; désormais accessible via le mode générique metric, une fois les noms exacts des métriques déterminés avec list-metrics --filter buffers
Débit de messages GET /api/system/throughput correct – déjà implémenté comme mode throughput (voir Comparaison OpenAPI)
Inputs GET /api/system/inputs le point de terminaison existe – /api/system/inputstates (déjà implémenté comme mode inputs) fournit en plus directement l'état de fonctionnement par input, c'est le choix le plus adapté pour une vérification
JVM Heap / GC / CPU / Pipeline / Thread Pools / Processing Rate GET /api/system/metrics/<namespace>.* Chemin incorrect – même problème de caractère générique pour les six ; désormais accessible de manière uniforme via le mode metric

En résumé : la sélection des métriques de ChatGPT est pertinente sur le fond et comble de véritables lacunes des cinq modes d'origine (notamment l'utilisation des buffers et l'accessibilité multi-nœuds étaient totalement absentes). En revanche, la syntaxe des points de terminaison pour tout ce qui relève de /system/metrics/... n'est pas correcte – l'API REST de Graylog ne connaît pas de chemins avec caractère générique comme org.graylog2.journal.*. Le mécanisme réel est le suivant :

  • GET /system/metrics/{metricName} – une valeur unique désignée exactement par son nom
  • GET /system/metrics/namespace/{namespace} – toutes les métriques d'un espace de noms (sans suffixe .*)
  • POST /system/metrics/multiple – une liste explicite de noms de métriques en une seule fois
  • GET /system/metrics/names – découverte : tous les noms disponibles

Ont été implémentées les deux propositions sûres au regard de la spécification et immédiatement reproductibles correctement (nodes pour l'état du cluster/des nœuds), ainsi qu'un mode générique metric accompagné d'un utilitaire de découverte list-metrics pour tout le reste (tas JVM, GC, CPU, buffers, pipeline, pools de threads) – voir Les huit modes, points 6–8. Volontairement, pas de mode codé en dur séparé avec des noms de champs devinés pour chaque famille de métriques, après que cela s'est déjà révélé erroné une fois avec utilization_ratio dans le mode journal (voir Comparaison OpenAPI) – les formes concrètes des réponses de métriques ne sont pas typées dans la spécification ; un mode générique est ici plus honnête que sept modes reposant sur des hypothèses non confirmées.

La vérification structurelle décrite dans Comparaison OpenAPI a maintenant été complétée par un véritable test en conditions réelles (runtime) : une instance Graylog réellement en fonctionnement plus une instance Icinga2 réellement en fonctionnement, toutes deux mises en place via Docker, le plugin entièrement testé et activé en production dans Icinga2.

Dans une installation Icinga2 Debian/Ubuntu classique (hors conteneur), c'est en général déjà présent.

Les deux bugs confirmés à l'identique en 7.1.3 Le test complet a été répété contre la bonne version après la découverte de la discordance de version (voir ci-dessus). Résultat : aucun des deux bugs trouvés n'était spécifique à 6.1 – les deux corrections (en-tête Accept pour lbstatus, permissions des métriques) restent nécessaires et efficaces sans changement en 7.1.3.

Bug 1 : lbstatus renvoyait HTTP 406 au lieu de l'information de statut

Résultat en conditions réelles avant correction : GRAYLOG UNKNOWN - load balancer status is HTTP 406. Cause : /system/lbstatus répond avec Content-Type: text/plain, mais le script envoyait systématiquement Accept: application/json pour tous les points de terminaison – Graylog refuse alors la réponse avec 406 Not Acceptable, au lieu de simplement fournir du texte brut. Correction : pour ce seul point de terminaison, Accept: */* au lieu de application/json.

Pourquoi cela n'est pas apparu lors de la comparaison OpenAPI Le test structurel précédent (voir Comparaison OpenAPI) s'est contenté de lire la spécification, sans jamais effectuer de véritable requête HTTP – un conflit d'en-tête Accept ne peut naturellement apparaître que dans un véritable cycle requête/réponse. C'est précisément la différence entre vérification structurelle et vérification en conditions réelles.

Bug 2 (en réalité : une lacune de permissions) : metric/list-metrics avec un token Reader seul

Résultat en conditions réelles avant correction : GRAYLOG UNKNOWN - .../system/metrics/names returned HTTP 403: Not authorized. Pas un bug dans le script, mais une lacune de permissions du rôle Reader dans Graylog – détails et correction voir Authentification plus haut.

Mise en place pour la production

Ce guide part du principe d'une installation Graylog et Icinga2 réelle (installation par paquet/système, pas la configuration de test Docker ci-dessus) – pour un environnement déjà en fonctionnement comme le vôtre.

  1. Créer un utilisateur Reader dans Graylog (interface web : System → Users → Create User, rôle « Reader »), ou via l'API : 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users" \
  -d '{"username":"icinga-monitoring","password":"<starkes-passwort>",
       "first_name":"Icinga","last_name":"Monitoring","email":"icinga@example.org",
       "roles":["Reader"],"permissions":[]}'
  2. Uniquement si metric/list-metrics doivent être utilisés : ajouter après coup les quatre permissions de métriques (voir Authentification pour la commande exacte et la manière de déterminer l'ID utilisateur).
  3. Générer un token API pour cet utilisateur : 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users/<user-id>/tokens/icinga-check"
    La réponse contient le token proprement dit dans le champ token – c'est la valeur à utiliser pour graylog_token dans Icinga2, pas le mot de passe de l'utilisateur.
  4. Copier check_graylog.py sur l'hôte Icinga2, par ex. vers /usr/lib/nagios/plugins/check_graylog.py. Python 3 et le paquet requests doivent y être présents (apt install python3-requests).
  5. Copier commands.conf.example et services-graylog.conf.example de ce dossier vers /etc/icinga2/conf.d/, en retirant l'extension .example.
  6. Dans le fichier Services copié, ou dans l'objet Host de votre instance Graylog, définir vars.graylog_url (l'URL racine de l'API, par ex. https://graylog.example.org:9000/api) et vars.graylog_token (le token de l'étape 3).
  7. Valider la configuration avant de recharger : 
    icinga2 daemon -C
  8. Recharger/redémarrer Icinga2. Après un intervalle de vérification, contrôler les services dans l'interface web Icinga, ou directement en ligne de commande : 
    icinga2 object list --type Service --name '<hostname>!graylog-*'
À prendre absolument en compte avant le déploiement en production
  • TLS : si votre instance Graylog tourne en HTTPS avec un certificat auto-signé, définir vars.graylog_insecure = true (ou mieux : déployer un véritable certificat).
  • Le mode journal a des seuils par défaut de 80 %/95 % – à adapter si nécessaire selon votre volume de messages en production ; les valeurs testées ici (0 %) ne disent rien de votre charge réelle.
  • Mode nodes : définir --expected-nodes sur le nombre réel de nœuds de votre cluster, sinon un nœud manquant ne sera pas détecté de manière fiable.

Points ouverts

  • Les tests ont été effectués contre une instance Graylog fraîche et vide, sans charge de messages réelle – les seuils (journal, throughput) ne sont pas encore validés contre une exploitation réelle en production
  • metric/list-metrics n'ont été testés qu'avec un seul exemple (jvm.memory.heap.usage) – pour toute autre métrique souhaitée (utilisation des buffers, etc.), la rechercher au préalable avec list-metrics et la vérifier individuellement avant utilisation
  • Le test multi-nœuds de nodes/--expected-nodes reste à faire (l'environnement de test ne comportait qu'un seul nœud Graylog)
