check_graylog.py – Documentación

Plugin de comprobación de Icinga2 para Graylog · proyecto hermano de graylog-checks/zabbix · Estado: julio de 2026

Guía de lectura GRAYLOG-CONCEPTS.html (un nivel más arriba) explica en detalle qué significan en la práctica los distintos valores de Graylog, por si Graylog es nuevo para ti; Los ocho modos explica qué comprueba concretamente el plugin y por qué; Verificación en vivo muestra los resultados reales de las pruebas contra una instancia de Graylog auténtica, incluidos dos errores encontrados y corregidos en el proceso; Configuración para el uso en producción es la guía paso a paso propiamente dicha para vuestro entorno real. El resto de la página es historia de génesis y decisiones, no imprescindible para la operación.

Objetivo

Icinga2 debe consultar periódicamente los estados más importantes de Graylog a través de su API REST, no limitarse a comprobar si "el proceso está en ejecución". Un servidor Graylog puede técnicamente estar en funcionamiento y encontrarse, aun así, en un estado que pronto provocará pérdida de datos (por ejemplo, un journal de mensajes lleno) — precisamente esos estados deben hacerse visibles con antelación.

Funcionamiento: convenciones de plugin de Nagios/Icinga2

Icinga2 no entiende ningún formato propio de plugin: invoca un programa de línea de comandos cualquiera e interpreta el código de salida y la salida estándar según un estándar establecido desde Nagios (la "Monitoring Plugins API").

Código de salidaSignificado
0OK
1WARNING
2CRITICAL
3UNKNOWN (p. ej. error de conexión, respuesta inesperada de la API)

La primera línea de salida es el mensaje de estado visible para Icinga. Opcionalmente, tras un | (pipe), sigue el Performance-Data con el formato etiqueta=valor;warn;crit;min;max — son los valores que Icinga/Grafana usan después para generar gráficas, sin tener que analizar el texto del mensaje. check_graylog.py sigue exactamente este esquema: 

GRAYLOG WARNING - journal utilization is 82.3% (14200 uncommitted entries) | utilization=82.3%;80.0;95.0;0;100 uncommitted_entries=14200;;;0 read_msgs_per_sec=310;;;0 write_msgs_per_sec=340;;;0

De ahí Icinga lee: estado = WARNING, mensaje de texto y cuatro valores medidos para las gráficas.

Un solo script, ocho modos en lugar de ocho scripts independientes El manejo de autenticación, el tratamiento de errores HTTP y el formateo de perfdata quedan así en un único lugar, en vez de duplicarse ocho veces.

Los ocho modos en detalle

1. lbstatus

EndpointGET /api/system/lbstatus
PropósitoEl estado de salud agregado propio de Graylog, pensado para los healthchecks de un balanceador de carga. La comprobación más barata y rápida.
RespuestaTexto plano ALIVE, THROTTLED o DEAD
MapeoALIVE→OK, THROTTLED→WARNING (Graylog frena deliberadamente la aceptación de nuevos mensajes, normalmente porque el indexador/journal está bajo presión), DEAD→CRITICAL

2. cluster

EndpointGET /api/system/indexer/cluster/health
PropósitoEstado del clúster de Elasticsearch/OpenSearch subyacente, donde Graylog almacena sus índices. Graylog en sí puede seguir funcionando mientras la búsqueda/indexación ya está afectada.
RespuestaJSON con status (green/yellow/red) y un objeto shards
Mapeogreen→OK, yellow→WARNING (normalmente shards de réplica ausentes — en un homelab de un solo nodo esto es permanentemente normal), red→CRITICAL (faltan shards primarios, un estado real de pérdida de datos)

3. journal

EndpointGET /api/system/journal
PropósitoEl verdadero indicador de alerta temprana. Graylog escribe primero los mensajes entrantes en un journal local (un registro de solo anexado al estilo Kafka) y solo después en el indexador. Si el indexador no da abasto, el journal crece en lugar de perder mensajes inmediatamente — pero solo hasta el tamaño de journal configurado.
RespuestaJSON con, entre otros, utilization_ratio (0.0–1.0), uncommitted_journal_entries, append_events_per_second, read_events_per_second, enabled
UmbralesWARNING por defecto a partir del 80 %, CRITICAL a partir del 95 % de ocupación (sobrescribibles con --warning/--critical). Si el journal está deshabilitado según la API → OK con texto informativo.
Por qué esta es la comprobación más importante cluster y lbstatus pueden seguir estando en verde mientras el journal ya se llena notablemente — ese es el primer síntoma medible, mucho antes de que algo se ponga en rojo.

4. inputs

EndpointGET /api/system/inputstates
PropósitoComprueba individualmente cada input configurado (p. ej. un listener de Syslog-UDP, un input GELF) en cuanto a su estado de ejecución — un único input caído no lo detectan cluster/lbstatus.
RespuestaLista JSON con state por input (RUNNING, FAILED, STOPPED, ...) y título
MapeoTodo RUNNING→OK. Algún input no RUNNING→CRITICAL, con el listado correspondiente. Ningún input configurado→WARNING.

5. throughput

EndpointGET /api/system/throughput
PropósitoMensajes por segundo a nivel de todo el clúster — principalmente para tendencias/gráficas, en segundo lugar como indicador de fallo ("la ingesta se ha detenido por completo").
UmbralesNinguno por defecto — 0 mensajes/s es normal en un homelab tranquilo. Si se fijan --warning/--critical, actúan como límite inferior (el problema es un valor por debajo).

6. nodes nuevo, 2026-07-23

EndpointGET /api/cluster
PropósitoResponde a "¿están realmente accesibles todos los nodos de Graylog?" — los cinco modos anteriores los responde siempre el único nodo al que la petición llega por azar, no el clúster completo. Un segundo nodo puede llevar tiempo caído sin que lbstatus/cluster/journal lo noten.
RespuestaDiccionario JSON node_id → SystemOverviewResponse (entre otros, hostname, lb_status, is_processing, lifecycle) — una entrada por cada nodo que respondió
MapeoCualquier nodo con lb_status != "ALIVE" o is_processing = false → CRITICAL. Opcionalmente --expected-nodes N: menos nodos de los esperados en la respuesta → CRITICAL (el caso en que un nodo falla por completo y por tanto ni siquiera aparece en el diccionario).

7. metric nuevo, 2026-07-23

EndpointGET /api/system/metrics/{metricName}
PropósitoAcceso genérico a una sola de las métricas internas de Dropwizard de Graylog — heap de la JVM, garbage collection, CPU, ocupación de ring buffers (Input/Process/Output), rendimiento del pipeline, thread pools. Un único modo en lugar de siete, porque Graylog no ofrece un endpoint con comodín para familias de métricas (véase Plantilla de ChatGPT: evaluación).
Parámetros--metric-name (obligatorio, nombre exacto, p. ej. jvm.memory.heap.usage), --field (ruta con puntos dentro del JSON, por defecto value), --warning/--critical
MapeoValor ≥ --critical → CRITICAL, ≥ --warning → WARNING, si no OK. Si falta --field en la respuesta → UNKNOWN.
Único punto del script sin garantía de especificación El esquema MetricsSummaryResponse/com.codahale.metrics.Metric está vacío en la especificación OpenAPI ({}) — las métricas de Dropwizard se serializan de forma distinta según su tipo (Gauge: value, Counter: count, Meter/Timer: objetos anidados rate/time), y eso ni siquiera está documentado en la propia especificación. El parámetro --field es por tanto un parámetro de mejor esfuerzo, no una estructura confirmada — verificar antes del uso en producción con list-metrics (más abajo) y un curl manual contra la instancia real.

8. list-metrics nuevo, 2026-07-23

EndpointGET /api/system/metrics/names
PropósitoNo es una comprobación real, sino una herramienta de descubrimiento: lista todos los nombres de métricas disponibles en la instancia (opcionalmente filtrados con --filter), para encontrar el nombre exacto para --mode metric --metric-name ... en lugar de adivinarlo.
MapeoSiempre OK — es un simple listado, sin evaluación.

Autenticación

La API REST de Graylog acepta tokens de API como HTTP Basic Auth, donde el propio token es el nombre de usuario y como contraseña se pasa la cadena fija y literal "token" (no es un placeholder — así lo especifica realmente Graylog). Además, el script añade en cada request la cabecera X-Requested-By (protección CSRF que la API de Graylog exige en algunas operaciones).

Privilegio mínimo Vincular el token a un usuario propio de Graylog con rol Reader, no a una cuenta de administrador — el token reside en el host de Icinga2.
Confirmado en vivo: el rol Reader NO es suficiente para metric/list-metrics En la prueba en vivo (véase Verificación en vivo) se comprobó que con el rol Reader puro los endpoints /system/metrics/* devuelven 403 Not authorized — lbstatus, cluster, journal, inputs, throughput y nodes funcionan sin problemas con Reader, pero los dos modos de métricas necesitan además cuatro permisos explícitos en el usuario: metrics:read, metrics:allkeys, metrics:readall, metrics:readhistory. Estos se pueden asignar directamente al usuario vía API (además del rol Reader, no en su lugar): 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'
El <user-id> es el ObjectId interno de MongoDB de Graylog, no el nombre de usuario — se puede obtener con GET /api/users/<username> (campo id). Quien solo necesite las seis comprobaciones básicas (sin metric/ list-metrics) puede omitir este paso.

Configuración en Icinga2

Dos archivos cubren esto:

  • commands.conf.example — define el objeto CheckCommand, que mapea las variables del DSL de Icinga2 ($graylog_url$, $graylog_token$, ...) a los argumentos de línea de comandos de check_graylog.py
  • services-graylog.conf.example — cinco reglas apply Service (una por modo), que se aplican a cada Host que tenga definido vars.graylog_url

En la práctica: check_graylog.py se coloca en el host Icinga2 bajo PluginDir (típicamente /usr/lib/nagios/plugins/), ambos archivos .conf.example se copian (eliminando la extensión .example) y se ajustan los valores de los placeholders (graylog_url, graylog_token, IP de destino).

Fuentes utilizadas

Importante para la valoración En esta sesión no se realizó ninguna búsqueda web ni consulta en vivo de la documentación oficial de Graylog.

El script se basa en conocimiento entrenado sobre:

  • La estructura de la API REST de Graylog (documentación oficial en docs.graylog.org, en particular los endpoints bajo /api/system/*) — proveniente de datos de entrenamiento, no consultada en vivo
  • Las "Nagios Plugin Development Guidelines" (Monitoring Plugins Project, monitoring-plugins.org) para códigos de salida y el formato de performance-data — igualmente de datos de entrenamiento
  • Conocimiento general sobre el DSL de Icinga2 (CheckCommand, apply Service)

Esto significa en concreto: las rutas de endpoint y los nombres de campos JSON utilizados (utilization_ratio, uncommitted_journal_entries, shards, ...) corresponden al estado que conozco por entrenamiento — pueden diferir ligeramente entre versiones de Graylog (Graylog cambia ocasionalmente detalles de la API REST entre versiones mayores).

Verificar antes del uso en producción Probar manualmente cada modo una vez contra la versión de Graylog realmente en ejecución, por ejemplo: 
curl -u <token>:token https://<graylog>:9000/api/system/journal
y comparar la estructura JSON con el formato esperado por el script.

Resultados y dos errores encontrados en el proceso: Verificación con OpenAPI (2026-07-23).

Verificación con OpenAPI (2026-07-23)

Raphael me proporcionó una exportación de la especificación de la API REST de Graylog: openapi.json (~1,1 MB, OpenAPI 3.1.0, 515 endpoints, versión de Graylog 7.1.3+c34604d), guardada directamente en esta carpeta. Con ello sí pudo realizarse la verificación reclamada en Fuentes utilizadas — ya no como un simple punto pendiente, sino como un contraste real entre suposición y especificación.

Los cinco endpoints usados por el plugin existen exactamente en las rutas esperadas. Resultado por modo:

ModoEndpointResultado
lbstatus /system/lbstatus error encontrado y corregido
journal /system/journal error encontrado y corregido
cluster /system/indexer/cluster/health confirmado correcto
inputs /system/inputstates confirmado correcto
throughput /system/throughput confirmado correcto

Error 1: lbstatus comunica el estado mediante el código de estado HTTP, no en el cuerpo

La suposición era que Graylog siempre devuelve HTTP 200 en /system/lbstatus y el estado real (ALIVE/THROTTLED/DEAD) como texto plano en el cuerpo de la respuesta. Según la especificación esto no es así: el estado va en el propio código de estado HTTP — 200=ALIVE, 429=THROTTLED, 503=DEAD.

Este era un error real: la función auxiliar común api_get() del script trataba cualquier código distinto de 200 como error de conexión (UNKNOWN) — THROTTLED y DEAD nunca se habrían reconocido como tales, sino que siempre se habrían reportado simplemente como "no se puede alcanzar Graylog". check_lbstatus() ahora hace su propia petición en lugar de pasar por api_get() y evalúa directamente el código de estado.

Error 2: journal no tiene un campo utilization_ratio

Toda la lógica de umbrales warning/crítico de check_journal() se basaba en un campo utilization_ratio (0.0–1.0) en la respuesta de /system/journal. Según el esquema JournalSummaryResponse de la especificación, ese campo simplemente no existe. En su lugar están disponibles journal_size y journal_size_limit (ambos en bytes) — la ocupación debe calcularse por sí misma: journal_size / journal_size_limit * 100. El script ahora lo hace así, con protección contra división por cero por si journal_size_limit llegara a ser 0.

Limitación importante de este contraste Fue un contraste estructural (qué campos existen, cómo se llaman, qué tipo tienen) basado en la especificación — no una prueba en tiempo de ejecución con valores reales de una instancia en funcionamiento. Si, por ejemplo, los umbrales warning/crítico del modo journal (80 %/95 %) reaccionan de forma razonable con valores reales, o si check_lbstatus() realmente recibe un 429 cuando Graylog aplica throttling, solo puede demostrarse contra una instancia en funcionamiento (véase Próximos pasos).

Plantilla de ChatGPT: evaluación (2026-07-23)

Raphael me proporcionó además original-chatgpt-proposal.txt — una lista de diez comprobaciones propuestas por ChatGPT. Contraste de cada propuesta contra la especificación OpenAPI real (openapi.json):

PropuestaEndpoint propuestoEvaluación
Estado del clúster GET /api/cluster correcto — existe exactamente así, ahora implementado como el modo nodes
Información de nodos GET /api/system/cluster/nodes el endpoint existe — /api/cluster (arriba) entrega directamente la misma información con estado de salud por nodo, por lo que se usa este en lugar de una segunda llamada
Ocupación del journal GET /api/system/metrics/org.graylog2.journal.* ruta incorrecta — las rutas con comodín no existen; ya está resuelto como modo propio journal mediante el endpoint dedicado /system/journal (mejor que el rodeo por métricas)
Buffer de Input/Process/Output GET /api/system/metrics/org.graylog2.buffers.*.* ruta incorrecta — mismo problema; ahora accesible mediante el modo genérico metric, una vez determinados los nombres exactos de métrica con list-metrics --filter buffers
Message Throughput GET /api/system/throughput correcto — ya implementado como modo throughput (véase Verificación con OpenAPI)
Inputs GET /api/system/inputs el endpoint existe — /api/system/inputstates (ya implementado como modo inputs) entrega además directamente el estado de ejecución por input, siendo la opción más adecuada para una comprobación
JVM Heap / GC / CPU / Pipeline / Thread Pools / Processing Rate GET /api/system/metrics/<namespace>.* ruta incorrecta — mismo problema de comodín para los seis; ahora accesibles de manera uniforme mediante el modo metric

En resumen: la selección de métricas de ChatGPT es técnicamente acertada y cubre lagunas reales que tenían los cinco modos originales (sobre todo faltaban por completo la ocupación de buffers y la accesibilidad multi-nodo). La sintaxis de endpoint para todo lo que está bajo /system/metrics/..., en cambio, no es correcta — la API REST de Graylog no conoce rutas con comodín como org.graylog2.journal.*. El mecanismo real es:

  • GET /system/metrics/{metricName} — un único valor nombrado exactamente
  • GET /system/metrics/namespace/{namespace} — todas las métricas bajo un espacio de nombres (sin sufijo .*)
  • POST /system/metrics/multiple — una lista explícita de nombres de métrica de una sola vez
  • GET /system/metrics/names — descubrimiento: todos los nombres disponibles

Se implementaron las dos propuestas seguras según la especificación, reproducibles correctamente de inmediato (nodes para estado de clúster/información de nodos), además de un modo genérico metric más un ayudante de descubrimiento list-metrics para todo el resto (JVM Heap, GC, CPU, buffers, pipeline, thread pools) — véase Los ocho modos, puntos 6-8. Deliberadamente no se creó un modo propio codificado para cada familia de métricas con nombres de campo adivinados, después de que precisamente eso fallara ya una vez con utilization_ratio en el modo journal (véase Verificación con OpenAPI) — las formas concretas de respuesta de las métricas no están tipadas en la especificación, y un modo genérico es aquí más honesto que siete modos con suposiciones no confirmadas.

La verificación estructural descrita en Verificación con OpenAPI se completó ahora con una auténtica prueba en tiempo de ejecución: una instancia de Graylog realmente en funcionamiento junto con una instancia de Icinga2 realmente en funcionamiento, ambas montadas con Docker, con el plugin probado por completo y activado en Icinga2.

Escenario de prueba

Montado en una VM de pruebas propia (HP1-icinga01, 192.168.10.35, 8 GB de RAM) en el clúster del homelab, todo mediante Docker Compose, sin instalación permanente en el sistema:

Resultado: ninguno de los dos errores encontrados era específico de 6.1 – ambas correcciones (cabecera Accept en lbstatus, permisos de métricas) son necesarias y eficaces sin cambios también en 7.1.3.

Error 1: lbstatus devolvía HTTP 406 en lugar de la información de estado

Resultado en vivo antes de la corrección: GRAYLOG UNKNOWN - load balancer status is HTTP 406. Causa: /system/lbstatus responde con Content-Type: text/plain, pero el script enviaba para todos los endpoints, sin distinción, Accept: application/json — Graylog entonces rechaza la respuesta con 406 Not Acceptable, en lugar de simplemente entregar texto plano. Corrección: para este endpoint concreto, Accept: */* en lugar de application/json.

Por qué esto no se detectó en la verificación con OpenAPI La prueba estructural anterior (véase Verificación con OpenAPI) solo leyó la especificación, nunca realizó una petición HTTP real — un conflicto de cabecera Accept solo se manifiesta, por naturaleza, en el ciclo real de petición/respuesta. Precisamente esa es la diferencia entre verificación estructural y verificación en tiempo de ejecución.

Error 2 (en realidad: laguna de permisos): metric/list-metrics con un token Reader puro

Resultado en vivo antes de la corrección: GRAYLOG UNKNOWN - .../system/metrics/names returned HTTP 403: Not authorized. No es un error del script, sino una laguna de permisos del rol Reader en Graylog — detalles y corrección en Autenticación más arriba.

Configuración para el uso en producción

Esta guía parte de una instalación real de Graylog e Icinga2 (instalación por paquetes/sistema, no el montaje de prueba con Docker de arriba) — para un entorno ya en funcionamiento como el vuestro.

  1. Crear un usuario Reader en Graylog (interfaz web: System → Users → Create User, rol "Reader"), o vía API: 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users" \
  -d '{"username":"icinga-monitoring","password":"<contraseña-fuerte>",
       "first_name":"Icinga","last_name":"Monitoring","email":"icinga@example.org",
       "roles":["Reader"],"permissions":[]}'
  2. Solo si van a usarse metric/list-metrics: añadir los cuatro permisos de métricas (véase Autenticación para el comando exacto y la obtención del ID de usuario).
  3. Generar un token de API para este usuario: 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users/<user-id>/tokens/icinga-check"
    La respuesta contiene el token propiamente dicho en el campo token — ese es el valor para graylog_token en Icinga2, no la contraseña del usuario.
  4. Copiar check_graylog.py al host de Icinga2, p. ej. a /usr/lib/nagios/plugins/check_graylog.py. Python 3 y el paquete requests deben estar presentes allí (apt install python3-requests).
  5. Copiar commands.conf.example y services-graylog.conf.example desde esta carpeta a /etc/icinga2/conf.d/, eliminando la extensión .example.
  6. En el archivo de servicios copiado o en el objeto Host de vuestra instancia de Graylog, fijar vars.graylog_url (la URL raíz de la API, p. ej. https://graylog.example.org:9000/api) y vars.graylog_token (el token del paso 3).
  7. Validar la configuración antes de recargar: 
    icinga2 daemon -C
  8. Recargar/reiniciar Icinga2. Tras un intervalo de comprobación, revisar los servicios en el frontend web de Icinga, o directamente por CLI: 
    icinga2 object list --type Service --name '<hostname>!graylog-*'
Tener muy en cuenta antes del despliegue en producción
  • TLS: si vuestra instancia de Graylog corre sobre HTTPS con un certificado autofirmado, fijar vars.graylog_insecure = true (o mejor: instalar un certificado real).
  • El modo journal tiene umbrales por defecto de 80 %/95 % — ajustarlos según el volumen de mensajes en producción; los valores probados aquí (0 %) no dicen nada sobre vuestro volumen real.
  • Modo nodes: fijar --expected-nodes al número real de nodos de vuestro clúster, de lo contrario un nodo ausente no se detectará de forma fiable.

Puntos pendientes

  • Las pruebas se realizaron contra una instancia de Graylog nueva y vacía, sin carga de mensajes real — los umbrales (journal, throughput) aún no están validados contra un funcionamiento productivo real
  • metric/list-metrics solo se probaron con un ejemplo (jvm.memory.heap.usage) — buscar otras métricas deseadas (ocupación de buffers, etc.) con list-metrics y verificarlas individualmente antes de usarlas
  • Aún falta la prueba multi-nodo de nodes/--expected-nodes (el entorno de prueba solo tenía un nodo de Graylog)
