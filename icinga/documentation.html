check_graylog.py – Documentation

Icinga2 check plugin for Graylog · sibling project to graylog-checks/zabbix · as of: July 2026

Reading roadmap GRAYLOG-CONCEPTS.html (one level up) explains in detail what the individual Graylog values actually mean, in case Graylog is new to you; The Eight Modes explains exactly what the plugin checks and why; Live Verification shows the actual test results against a real Graylog instance, including two bugs found and fixed along the way; Setup for Production Use is the actual step-by-step guide for your real environment. The rest of the page is background on how this came about and the decisions made along the way — not strictly necessary for operations.

Goal

Icinga2 should regularly poll the most important Graylog states via its REST API, not just check "is the process running." A Graylog server can technically be up and still be in a state that will soon lead to data loss (e.g. a full message journal) — exactly these kinds of states should become visible early.

How It Works: Nagios/Icinga2 Plugin Conventions

Icinga2 has no plugin format of its own — it calls an arbitrary command-line program and interprets the exit code and standard output according to a standard established since Nagios (the "Monitoring Plugins API").

Exit codeMeaning
0OK
1WARNING
2CRITICAL
3UNKNOWN (e.g. connection error, unexpected API response)

The first output line is the status message visible to Icinga. Optionally, after a | (pipe), performance data follows in the format label=value;warn;crit;min;max — these are the values that Icinga/Grafana later use for graphs without having to parse the text message. check_graylog.py follows exactly this schema: 

GRAYLOG WARNING - journal utilization is 82.3% (14200 uncommitted entries) | utilization=82.3%;80.0;95.0;0;100 uncommitted_entries=14200;;;0 read_msgs_per_sec=310;;;0 write_msgs_per_sec=340;;;0

Icinga reads from this: status = WARNING, text message, and four measurements for the graphs.

One script, eight modes instead of eight separate scripts Auth handling, HTTP error handling and perfdata formatting stay in one place, instead of being duplicated eight times over.

The Eight Modes in Detail

1. lbstatus

EndpointGET /api/system/lbstatus
PurposeGraylog's own, aggregated health status, intended for load-balancer health checks. The cheapest, fastest check.
ResponsePlain text ALIVE, THROTTLED, or DEAD
MappingALIVE→OK, THROTTLED→WARNING (Graylog is deliberately throttling acceptance of new messages, usually because the indexer/journal is under pressure), DEAD→CRITICAL

2. cluster

EndpointGET /api/system/indexer/cluster/health
PurposeState of the underlying Elasticsearch/OpenSearch cluster that Graylog stores its indices on. Graylog itself can be running while search/indexing is already disrupted.
ResponseJSON with status (green/yellow/red) and a shards object
Mappinggreen→OK, yellow→WARNING (usually missing replica shards — permanently normal in a single-node homelab setup), red→CRITICAL (primary shards missing, a genuine data-loss state)

3. journal

EndpointGET /api/system/journal
PurposeThe actual early-warning indicator. Graylog first writes incoming messages to a local journal (a Kafka-like append-only log) and only from there into the indexer. If the indexer can't keep up, the journal grows instead of messages being lost immediately — but only up to the configured journal size.
ResponseJSON including utilization_ratio (0.0–1.0), uncommitted_journal_entries, append_events_per_second, read_events_per_second, enabled
ThresholdsDefault WARNING at 80 %, CRITICAL at 95 % utilization (overridable via --warning/--critical). Journal disabled according to the API → OK with an informational message.
Why this is the most important check cluster and lbstatus can both still be green while the journal is already filling up noticeably — that's the first measurable symptom, before anything even turns red.

4. inputs

EndpointGET /api/system/inputstates
PurposeChecks each configured input (e.g. a syslog UDP listener, a GELF input) individually for its running state — a single crashed input is not detected by cluster/lbstatus.
ResponseJSON list with state per input (RUNNING, FAILED, STOPPED, ...) and title
MappingEverything RUNNING→OK. Any input not RUNNING→CRITICAL, with a listing. No inputs configured→WARNING.

5. throughput

EndpointGET /api/system/throughput
PurposeCluster-wide messages/second — primarily for trending/graphs, secondarily as an outage indicator ("ingestion has come to a complete standstill").
ThresholdsNone by default — 0 messages/s is normal in a quiet homelab. If --warning/--critical are set, they act as a lower bound (a value below them is the problem).

6. nodes new, 2026-07-23

EndpointGET /api/cluster
PurposeAnswers "are really all Graylog nodes reachable" — the five modes above are all answered by exactly the one node the request happens to hit, not by the entire cluster. A second node could already be gone entirely without lbstatus/cluster/journal noticing.
ResponseJSON dictionary node_id → SystemOverviewResponse (including hostname, lb_status, is_processing, lifecycle) — one entry per node that responded
MappingAny node with lb_status != "ALIVE" or is_processing = false → CRITICAL. Optional --expected-nodes N: fewer nodes than expected in the response → CRITICAL (the case when a node fails completely and therefore doesn't even show up in the dictionary).

7. metric new, 2026-07-23

EndpointGET /api/system/metrics/{metricName}
PurposeGeneric access to a single one of Graylog's internal Dropwizard metrics — JVM heap, garbage collection, CPU, ring-buffer utilization (input/process/output), pipeline performance, thread pools. One mode instead of seven, because Graylog doesn't offer a wildcard endpoint for metric families (see ChatGPT Template: Assessment).
Parameters--metric-name (required, exact name, e.g. jvm.memory.heap.usage), --field (dotted path into the JSON, default value), --warning/--critical
MappingValue ≥ --critical → CRITICAL, ≥ --warning → WARNING, otherwise OK. --field missing in the response → UNKNOWN.
The one place in the script without a specification guarantee The MetricsSummaryResponse/com.codahale.metrics.Metric schema is empty in the OpenAPI specification ({}) — Dropwizard metrics serialize differently depending on type (Gauge: value, Counter: count, Meter/Timer: nested rate/time objects), and even the specification doesn't document this. The --field path is therefore a best-effort parameter, not a confirmed structure — verify it before production use with list-metrics (below) and a manual curl against the real instance.

8. list-metrics new, 2026-07-23

EndpointGET /api/system/metrics/names
PurposeNot a real check, but a discovery tool: lists all metric names available on the instance (optionally filtered with --filter), so you can find the exact name for --mode metric --metric-name ... instead of guessing it.
MappingAlways OK — pure listing, no evaluation.

Authentication

Graylog's REST API accepts API tokens as HTTP Basic Auth, where the token itself is the username and the fixed, literal string "token" is passed as the password (not a placeholder — that's actually how Graylog specifies it). In addition, the script sets the X-Requested-By header on every request (CSRF protection that Graylog's API requires for some operations).

Least privilege Bind the token to a dedicated Graylog user with the Reader role, not to an admin account — the token lives on the Icinga2 host.
Confirmed live: the Reader role is NOT enough for metric/list-metrics The live test (see Live Verification) showed: with a pure Reader role, the /system/metrics/* endpoints return 403 Not authorized — lbstatus, cluster, journal, inputs, throughput, and nodes work fine with Reader, but the two metric modes additionally need four explicit permissions on the user: metrics:read, metrics:allkeys, metrics:readall, metrics:readhistory. These can be set directly on the user via the API (in addition to the Reader role, not as a replacement): 
curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X PUT "http://<graylog>:9000/api/users/<user-id>" \
  -d '{"permissions": ["metrics:read","metrics:allkeys","metrics:readall","metrics:readhistory"]}'
The <user-id> is Graylog's internal MongoDB ObjectId, not the username — retrievable via GET /api/users/<username> (field id). Anyone who only needs the six basic checks (no metric/list-metrics) can skip this step.

Configuration in Icinga2

Two files cover this:

  • commands.conf.example – defines the CheckCommand object that maps the Icinga2 DSL variables ($graylog_url$, $graylog_token$, ...) onto the CLI arguments of check_graylog.py
  • services-graylog.conf.example – five apply Service rules (one per mode) that apply to every Host with vars.graylog_url set

In practice: check_graylog.py ends up on the Icinga2 host under PluginDir (typically /usr/lib/nagios/plugins/), both .conf.example files are copied (dropping the .example suffix), and the placeholder values (graylog_url, graylog_token, target IP) are adjusted.

Sources Used

Important context In this session, no web search and no live lookup of the official Graylog documentation was performed.

The script is based on trained knowledge of:

  • Graylog's REST API structure (official docs at docs.graylog.org, in particular the endpoints under /api/system/*) – from training data, not looked up live
  • The "Nagios Plugin Development Guidelines" (Monitoring Plugins Project, monitoring-plugins.org) for exit codes and performance-data format – also from training data
  • General knowledge of Icinga2's DSL (CheckCommand, apply Service)

Concretely, that means: the endpoint paths and JSON field names used (utilization_ratio, uncommitted_journal_entries, shards, ...) correspond to what I know from training – they may differ slightly between Graylog versions (Graylog occasionally changes REST API details between major versions).

Verify before production use Test each mode by hand once against the actually running Graylog version, e.g.: 
curl -u <token>:token https://<graylog>:9000/api/system/journal
and compare the JSON structure against the format expected by the script.

OpenAPI Cross-Check (2026-07-23)

Raphael provided me with an export of the Graylog REST API specification: openapi.json (~1.1 MB, OpenAPI 3.1.0, 515 endpoints, Graylog version 7.1.3+c34604d), placed directly in this folder. This made it possible to actually carry out the verification called for in Sources Used — no longer just an open item, but a real comparison of assumption against specification.

All five endpoints used by the plugin exist exactly at the expected paths. Result per mode:

ModeEndpointResult
lbstatus /system/lbstatus Bug found & fixed
journal /system/journal Bug found & fixed
cluster /system/indexer/cluster/health confirmed correct
inputs /system/inputstates confirmed correct
throughput /system/throughput confirmed correct

Bug 1: lbstatus communicates via the HTTP status code, not the body

The assumption was that Graylog always returns HTTP 200 for /system/lbstatus, with the actual status (ALIVE/THROTTLED/DEAD) as plain text in the response body. According to the specification, that's not correct: the state is encoded in the HTTP status code itself – 200=ALIVE, 429=THROTTLED, 503=DEAD.

This was a real bug: the script's shared api_get() helper function treated every non-200 code as a connection error (UNKNOWN) – THROTTLED and DEAD would therefore never have been recognized as such, only ever reported as "can't reach Graylog." check_lbstatus() now makes its own request instead of going through api_get(), and evaluates the status code directly.

Bug 2: journal has no utilization_ratio field

The entire warn/crit threshold logic of check_journal() relied on a field utilization_ratio (0.0–1.0) in the response from /system/journal. According to the JournalSummaryResponse schema in the specification, this field simply doesn't exist. Instead there are journal_size and journal_size_limit (both in bytes) – the utilization has to be calculated manually: journal_size / journal_size_limit * 100. The script now does exactly that, with a guard against division by zero in case journal_size_limit is ever 0.

Important limitation of this cross-check This was a structural comparison (which fields exist, what they're called, what type they have) against the specification – not a runtime test with real values from a running instance. Whether, for instance, the warn/crit thresholds in journal mode (80 %/95 %) react sensibly against real values, or whether check_lbstatus() actually gets a 429 when Graylog throttles, can only be shown against a running instance (see Next Steps).

ChatGPT Template: Assessment (2026-07-23)

Raphael also provided me with original-chatgpt-proposal.txt – a list of ten checks proposed by ChatGPT. Each proposal cross-checked against the real OpenAPI specification (openapi.json):

ProposalProposed endpointAssessment
Cluster status GET /api/cluster correct – exists exactly as such, now implemented as mode nodes
Node information GET /api/system/cluster/nodes endpoint exists – /api/cluster (above) delivers the same information directly, with health status per node, so that one was used instead of a second call
Journal utilization GET /api/system/metrics/org.graylog2.journal.* Path wrong – wildcard paths don't exist; already solved as its own mode journal via the dedicated /system/journal endpoint (better than the metrics detour)
Input/Process/Output buffer GET /api/system/metrics/org.graylog2.buffers.*.* Path wrong – same problem; now retrievable via the generic mode metric, once the exact metric names have been found with list-metrics --filter buffers
Message throughput GET /api/system/throughput correct – already implemented as mode throughput (see OpenAPI Cross-Check)
Inputs GET /api/system/inputs endpoint exists – /api/system/inputstates (already implemented as mode inputs) additionally delivers the running state per input directly, making it the better choice for a check
JVM heap / GC / CPU / pipeline / thread pools / processing rate GET /api/system/metrics/<namespace>.* Path wrong – same wildcard problem for all six; now uniformly retrievable via mode metric

In short: ChatGPT's choice of metrics is technically sound and covers real gaps that the original five modes had (in particular buffer utilization and multi-node reachability were missing entirely). The endpoint syntax for everything under /system/metrics/... is not correct, though – Graylog's REST API has no wildcard paths like org.graylog2.journal.*. The actual mechanism:

  • GET /system/metrics/{metricName} – a single, exactly named value
  • GET /system/metrics/namespace/{namespace} – all metrics under a namespace (no .* suffix)
  • POST /system/metrics/multiple – an explicit list of metric names at once
  • GET /system/metrics/names – discovery: all available names

The two specification-safe proposals that could be rebuilt immediately and correctly were implemented (nodes for cluster status/node info), along with a generic metric mode plus a list-metrics discovery helper for everything else (JVM heap, GC, CPU, buffers, pipeline, thread pools) – see The Eight Modes, items 6–8. Deliberately not a separate, hard-coded mode with guessed field names for every single metric family, after exactly that already went wrong once with utilization_ratio in journal mode (see OpenAPI Cross-Check) – the concrete metric response shapes aren't typed in the specification, and a generic mode is more honest here than seven modes built on unconfirmed assumptions.

Result: neither of the two bugs found was 6.1-specific – both fixes (Accept header for lbstatus, metrics permissions) are still necessary and effective at 7.1.3, unchanged.

Bug 1: lbstatus returned HTTP 406 instead of the status information

Live result before the fix: GRAYLOG UNKNOWN - load balancer status is HTTP 406. Cause: /system/lbstatus responds with Content-Type: text/plain, but the script sent Accept: application/json uniformly for all endpoints – Graylog then refuses the response with 406 Not Acceptable instead of simply delivering plain text. Fix: for this one endpoint, Accept: */* instead of application/json.

Why this wasn't caught by the OpenAPI cross-check The earlier structural test (see OpenAPI Cross-Check) only read the specification, never made a real HTTP request – an Accept-header conflict naturally only shows up in an actual request/response cycle. That's exactly the difference between structural verification and runtime verification.

Bug 2 (really a permission gap): metric/list-metrics with a pure Reader token

Live result before the fix: GRAYLOG UNKNOWN - .../system/metrics/names returned HTTP 403: Not authorized. Not a bug in the script, but a permission gap in Graylog's Reader role – details and fix in Authentication above.

Setup for Production Use

This guide assumes a real Graylog and Icinga2 installation (package/system installation, not a Docker test setup like above) – for an already-running environment like yours.

  1. Create a Reader user in Graylog (web UI: System → Users → Create User, role "Reader"), or via the API: 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users" \
  -d '{"username":"icinga-monitoring","password":"<strong-password>",
       "first_name":"Icinga","last_name":"Monitoring","email":"icinga@example.org",
       "roles":["Reader"],"permissions":[]}'
  2. Only if metric/list-metrics are to be used: add the four metrics permissions afterwards (see Authentication for the exact command and how to find the user ID).
  3. Generate an API token for this user: 
    curl -u admin:<adminpw> -H "X-Requested-By: cli" -H "Content-Type: application/json" \
  -X POST "http://<graylog>:9000/api/users/<user-id>/tokens/icinga-check"
    The response contains the actual token in the token field – this is the value for graylog_token in Icinga2, not the user's password.
  4. Copy check_graylog.py onto the Icinga2 host, e.g. to /usr/lib/nagios/plugins/check_graylog.py. Python 3 + the requests package must be present there (apt install python3-requests).
  5. Copy commands.conf.example and services-graylog.conf.example from this folder to /etc/icinga2/conf.d/, dropping the .example suffix.
  6. In the copied services file, or in the Host object for your Graylog instance, set vars.graylog_url (the API root URL, e.g. https://graylog.example.org:9000/api) and vars.graylog_token (the token from step 3).
  7. Validate the configuration before reloading: 
    icinga2 daemon -C
  8. Reload/restart Icinga2. After one check interval, review the services in the Icinga web frontend, or directly via CLI: 
    icinga2 object list --type Service --name '<hostname>!graylog-*'
Be sure to consider before rolling out to production
  • TLS: if your Graylog instance runs on HTTPS with a self-signed certificate, set vars.graylog_insecure = true (or better: install a real certificate).
  • The journal mode has default thresholds of 80 %/95 % – adjust as needed for your production message volume; the values tested here (0 %) say nothing about your real volume.
  • nodes mode: set --expected-nodes to the actual node count of your cluster, otherwise a missing node won't be reliably detected.

Open Items

  • Testing was done against a fresh, empty Graylog instance with no real message load – thresholds (journal, throughput) have not yet been validated against real production operation
  • metric/list-metrics were only tested with one example (jvm.memory.heap.usage) – search for further desired metrics (buffer utilization etc.) with list-metrics and verify them individually before use
  • A multi-node test of nodes/--expected-nodes is still outstanding (the test environment had only a single Graylog node)
